## Step 3: Store
- Branch: feat/store
- Date: 2026-10-30
- Spec: §9, §4.2 (shared data), §10 (store tags), §11 (store tests)
- Done: `src/core/store/idb.ts`, a promise wrapper over IndexedDB without a library: `requestResult`, `walk` (cursor with direction and range, stops when the visitor returns `false`) and `transact` (runs `work` in one transaction, resolves after commit, rolls back and rejects with the first error, and takes `{ signal }`, whose reason becomes the rejection). `migrations.ts`: `MIGRATIONS` (migration N is entry N-1) and migration 1, which creates the five stores and the indexes of §9 exactly, including the unique `[source_key, fingerprint]` and `[error_type, created_at]` on `error_events`. `open.ts`: `openDatabase(factory, { name, migrations, signal })` runs the missing migrations in order from `onupgradeneeded`, fails with `DatabaseOpenFailed` (including a newer stored version and `open` throwing) or `MigrationFailed` (a migration threw, which rolls the upgrade back; or the upgrade is blocked), closes a connection that arrives after a blocked or cancelled open, and sets `onversionchange` to close the connection. `store.ts`: `Store(db, clock, { validateConfig })` with configs (list by name, get, create, update, delete), documents (list by `updated_at` descending, get, create, update, rename, delete) and settings (`getSetting`, `getSettings`, `setSetting`, typed per key). `settings.ts`: the ten keys with defaults, decode and encode rules. `types.ts`: the records. `index.ts`: the public exports. `src/platform/channel.ts`: the `ChangeChannel` interface for the four messages of §4.2, `BroadcastChangeChannel` over `BroadcastChannel("english-tutor")` (ignores messages that are not one of the four), and `src/platform/testing/fake-channel.ts` (`FakeChannelBus` / `FakeChangeChannel`). `core/store/testing/db.ts` makes a fresh `fake-indexeddb` database and store per test. Tests (table-driven, 244 new): schema and indexes per store, migrations from empty / from an older version / current, blocked and failing migrations, `versionchange`, transaction commit, rollback and cancel, CRUD per area, ordering, the route of every tag, defaults for missing and invalid settings, setter refusals, cancelling, and the channel (real `BroadcastChannel` in Node, and the fake). The six store tags were removed from the allow-list of `specs.test.ts`; 17 tags remain in it (`SettingInvalid` is new and has its route test).
- Screenshots: none: no UI in this step
- Checks: format:check, typecheck, lint, test (14 files, 339 tests), build, lint:ext (0 errors, 0 notices, 0 warnings) and screenshots (3 scenarios, exit 0; the PNGs of step 2 are unchanged) all pass.
- Notes:
  - Spec changes (§9, §10): a new tag `SettingInvalid` (`store`): a setter refuses a value its key does not allow, so that a stored setting always reads back as set; reading still never fails and gives the default. Index names are given (the key path fields joined by `_`: `source_key_fingerprint`, `error_type_created_at`), `line_ending` is `"lf"` or `"crlf"`, optional numbers are `null` and unset text is `""`. `pane_sizes` is stored as the array `[editor, issues]` (the spec said JSON, which is a string in a database that stores structured data), each above 0 and below 100. Other invalid rules written out: delay outside 1 to 60, a family over 100 characters, and a selected LLM id that is not a positive integer or null. Sizes and delay accept non-integers. The text about the validator was added to §9.
  - The seam for config validation is the `validateConfig` option of the `Store` constructor (`ConfigValidator`, throws `LLMConfigInvalid`); the default checks nothing. Step 4 passes the real one. The store validates no values of its own.
  - `deleteConfig` does not touch `selected_llm_id`; choosing the next selection (§4.7) is for the options page, which sets the setting afterwards.
  - `renameDocument` also sets `updated_at`, so a renamed document moves to the top of the library list. `listDocuments` returns whole documents, content included.
  - A unique name violation (`ConstraintError`) becomes `LLMConfigNameTaken` in the same transaction, with no pre-check read. Its metadata is empty, because names are user text.
  - A cancelled call (`{ signal }`, accepted by every `Store` method and `openDatabase`) rejects with the signal's reason and is never an `AppError`; the transaction is rolled back. A `DatabaseQueryFailed` test uses a closed connection and a value that cannot be cloned.
  - `Store` does not post on the channel. The page that changes data posts the message after the call, as §4.2 says; nothing in `src/core` touches `BroadcastChannel` or `browser.*`. The fake bus delivers synchronously; the real channel does not deliver a message back to its poster.
  - `eslint-disable` for `prefer-promise-reject-errors` is used in `idb.ts` and `open.ts` only: IndexedDB errors and abort reasons are rejected unchanged. The spec test ignores files named `errors.test.ts`, so the query-failure route tests live in `queries.test.ts`.
