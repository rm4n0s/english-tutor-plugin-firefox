# English Tutor for Firefox: Specification

Status: draft v0.1

## 1. Purpose

A Firefox extension for practising written English. It does in the browser what the desktop application [English Tutor](https://github.com/rm4n0s/english-tutor) does on Linux. The user writes a sentence or an essay in the extension's editor page. An LLM finds grammar, vocabulary and syntax errors, and the editor underlines them, with a different colour and line style for each category. When the user selects an error, a side panel explains why it is wrong and shows better alternatives, rendered from the LLM's markdown. The extension counts how often the user makes each kind of mistake, so the user can see what to work on.

The extension also checks what the user writes in text boxes on web pages, if the user turns that on (page mode, section 4.11): it underlines the errors inside the text box, shows the number of errors on a badge, and shows the LLM's explanation of an error in a dialog or when the user clicks the underline. And it adds entries to the right-click menu of web pages, so text selected on any page can be checked in the editor page.

## 2. Goals and non-goals

**Goals**
- Write English text in a plain editor page, with LLM-detected errors underlined and coloured by category.
- Learn from each error: a markdown explanation and better alternatives, next to the editor.
- Ask for other ways to write a selected word, sentence or paragraph, from the editor's right-click menu (sections 4.6 and 5.10).
- Send text selected on any web page to the editor page and check it there (section 4.1).
- Check text boxes on web pages in place, with underlines, an error-count badge, an issues dialog and an explanation popover (page mode, section 4.11).
- Choose which LLM is used from a selector above the editor, and manage the LLM list on the options page.
- Open and download text files, and keep documents in a library inside the extension.
- Count mistakes by error type, so the user sees which mistakes they repeat.
- Behave like the desktop application wherever a browser allows it. Section 2.2 lists every place where it differs.

**Non-goals (v1)**
- Page mode (section 4.11) never changes the text of a web page: it does not apply corrections or alternatives inside a text box. The Alternatives panel exists only in the tutor page.
- No checking of rich editors that draw their own text without a text box or `contenteditable` (for example canvas-based editors such as Google Docs).
- No rich text formatting; the editor is plain text.
- No offline or rule-based checker; every error comes from the LLM.
- No language other than English as the text being checked. Explanations are in English.
- No accounts, no sync (`storage.sync` is not used), and no cloud storage of the extension's own.
- No browser other than Firefox for desktop. No Firefox for Android, no Chrome build.
- No lessons, exercises or grades. Progress tracking is limited to the per-error-type counts (section 5.7).
- No equivalent of the desktop application's web server, system tray, single-instance lock or desktop entry.
- No private browsing: the extension sets `"incognito": "not_allowed"`, so it does not run in private windows.

### 2.1 Reference implementation

The desktop application is the reference for everything this spec says is "as in the desktop app": prompts, reply parsing, locating, chunking, the error taxonomy and its labels, fingerprints, and the statistics rules. The port follows tag `v0.1.3` (commit `92467a068d8876085482775adc90df5e6657b541`) of `github.com/rm4n0s/english-tutor`. Its `docs/SPEC.md` is called *desktop SPEC* below.

The prompts (check, retry reminder, explanation, alternatives, Test connection) are copied word for word from `internal/analysis` at that commit, so that a model behaves the same in both applications. A later change to the desktop prompts is ported on purpose, as its own change, and this section is updated to the new commit.

## 3. Technology

### 3.1 Dependencies

No runtime dependencies: the shipped extension contains only this project's code.

These development dependencies are approved: `typescript`, `esbuild`, `vitest`, `happy-dom`, `fake-indexeddb`, `eslint`, `@eslint/js`, `typescript-eslint`, `prettier`, `web-ext`, `@types/firefox-webext-browser` (the type definitions of the `browser` namespace), and `selenium-webdriver` (the screenshot harness drives a headless Firefox with it; its Selenium Manager downloads geckodriver). Anything else needs the user's approval before it is added (CLAUDE.md).

### 3.2 Manifest and permissions

- `browser_specific_settings.gecko.id`: `english-tutor@rm4n0s.dev`. `strict_min_version` is `140.0`. `gecko.data_collection_permissions` is `{"required": ["websiteContent"]}`: the text the user checks (typed, or selected on a web page) is sent to the LLM server the user configures. `web-ext lint` and AMO require the key, and it needs Firefox 140 or newer on desktop. `gecko_android.strict_min_version` is `142.0` only because `web-ext lint` demands it once `data_collection_permissions` is set; Firefox for Android is still not supported (section 2).
- `background.scripts`: one bundled script (an event page; Firefox MV3 has no service worker requirement).
- `action`: toolbar button with the extension's icon and the title "English Tutor".
- `options_ui`: `options.html`, `open_in_tab: true`.
- `commands`: `open-tutor`, suggested key `Alt+Shift+E`. The user can change it in `about:addons`.
- `content_security_policy.extension_pages`: the MV3 default (`script-src 'self'`), plus `style-src 'self'`. No inline script, no `eval`, no remote code.
- `incognito`: `not_allowed`.
- `permissions`: `storage` (`storage.session` for the hand-off, section 4.1, the page-mode frame registrations and the sites answered Not now, section 4.11, and the Not-an-error ignore set, section 5.7), `menus` and `menus.overrideContext` (the web page and toolbar button menus of the background script, section 4.1, and the context menus of the editor and of the issues list, sections 4.3 and 4.4: `menus.overrideContext` is a permission of its own, and calling it without it fails because the function does not exist; the `tab` context it also offers needs `tabs`, which the extension does not ask for and does not use), `notifications` (the check-finished message, section 4.10), `downloads`, `scripting` (to register the page-mode content script only while page mode is on, section 4.11).
- `optional_host_permissions`: `http://*/*`, `https://*/*`, `<all_urls>`. Nothing is granted at install. The options page asks for the origin of one LLM's base URL when that LLM is saved or tested (section 4.7), and for `<all_urls>` only when the user turns page mode on (section 4.11); turning page mode off removes it.
- `web_accessible_resources`: `[{ "resources": ["page-ui.html", "page-ui.js", "page-ui.css"], "matches": ["<all_urls>"] }]`, so the content script can load the page-mode frame (section 4.11). Firefox gives every install its own random `moz-extension://` address, so the address does not identify the extension across users.
- No static `content_scripts`, no `tabs`, no `activeTab`, and no `host_permissions`. Adding a permission is a change to this section.

## 4. User interface

### 4.1 Entry points

- **Toolbar button** and the **`open-tutor` command**: bring the most recently focused tutor tab to the front (its tab and its window). If no tutor tab is open, open one in the current window. The button's context menu (`menus` context `action`) adds **New tutor tab** (always opens one) and **Preferences**.
- **Web page context menu**: when text is selected on a page (`menus` context `selection`), two entries in an "English Tutor" submenu. The entries are made for web pages only (`documentUrlPatterns` `http://*/*`, `https://*/*` and `file:///*`), so they do not show in the tutor page, whose editor has its own menu (section 4.3), or in other extension pages:
  - **Check with English Tutor**: opens a new tutor tab, right after the tab the menu was used in, with the selection as a new text (a new `session:` source) and starts a manual check of the whole text (only if an LLM is selected; otherwise the text is just loaded and the explanation panel shows the no-LLM hint).
  - **Alternatives with English Tutor**: opens a new tutor tab with the selection as a new text, selects all of it, and opens the Alternatives panel for it (section 4.6). The entry is always offered: Firefox gives `menus.onShown` no selection text (only the click has it, and that needs no permission), so the menu cannot hide the entry for a selection over 600 words. For such a selection the panel fails with `SelectionTooLong` and its message, and the whole text is there to cut down.
  - A selection that is empty or only white space does nothing.
  - The background script makes these entries and the button's when the extension is installed, updated or loaded (`runtime.onInstalled`) and when the browser starts (`runtime.onStartup`); the browser keeps them while the event page is stopped. It removes its own ids before it makes them, so a second run does not fail with a duplicate id, and it leaves the entries that the tutor pages made alone. A failure is `ContextMenuFailed`, logged.
- **Hand-off.** The background script never puts the text in a URL (that would put it in the history). It stores `{ text, action, at }` (`action` is `check` or `alternatives`, `at` is the time in milliseconds) in `storage.session` under the key `handoff:<uuid>` (a random UUID) and opens `tutor.html#handoff=<uuid>`. The tutor page reads the entry, deletes it, and clears the fragment with `history.replaceState` before it does anything else, so a reload does not look for it again. The loaded text is a new text with no name and a new `session:` source, and counts as nothing unsaved (it is a copy of text still on the web page). A fragment that is not exactly `#handoff=` and a UUID is ignored. An entry that is missing, unreadable or already taken (for example after a browser restart, or when the address is opened a second time) shows `HandoffExpired` in the banner and leaves the text as it was. Entries older than 5 minutes (the exact 5 minutes still count) are deleted by the background script every time it starts, which for an event page is each time the browser wakes it (a menu click, the toolbar button, a notification, an update).
- The selection comes from `info.selectionText` of the menu click. Firefox can shorten very long selections there. This is accepted in v1 (section 13).
- **Finding tutor tabs** without the `tabs` permission: each tutor page learns its own tab id and window id with `tabs.getCurrent()`, records the time it was last focused, and answers the message `{ type: "tutor-ping" }` with `{ tabId, windowId, focusedAt, dirty }` (`dirty`: the tab has unsaved changes, section 4.2). A tab counts as focused (`focusedAt` is the time, from the injected `Clock`) when it opens visible, when its window gets the focus and when it becomes the visible tab again; a tab that opens in the background has `focusedAt` 0. `runtime.sendMessage` reaches every page but returns only the first answer, so the background script calls `tabs.query({})` (which needs no permission and returns ids without addresses) and sends the ping to each tab with `tabs.sendMessage`; tabs without a tutor page have no receiver, and their error is ignored. It focuses the tutor tab with the latest `focusedAt` (the higher tab id on a tie) with `tabs.update(tabId, { active: true })` and `windows.update(windowId, { focused: true })`.

### 4.2 Tutor page

```
+----------------------------------------------------------------------+
| LLM: [ Claude Sonnet v ]  [Check]  [ ] Auto-check  [Stats] [Prefs]   |
| [New] [Open] [Save] [Save As] [Save to library] [Library]            |
| Legend:  ~~ grammar   -- vocabulary   .. syntax        [Clear][Copy] |
+----------------------------------------+-----------------------------+
| ! banner (failures, dismissible)       | Issues (3)                  |
|                                        | [G] He go to school         |
|  Text editor                           | [V] make a photo            |
|  (errors underlined by category)       | [S] I very like it          |
|                                        |-----------------------------|
|                                        | Subject-verb agreement      |
|                                        | Markdown explanation of     |
|                                        | the selected issue          |
+----------------------------------------------------------------------+
| 3 issues | 142 words | last: 812 in / 164 out · session: 5.2k / 1.1k  |
+----------------------------------------------------------------------+
```

- The editor and the right column are separated by a draggable divider; the right column has a second divider between the issues list and the explanation panel. Both positions are remembered (`pane_sizes`, section 9): they are saved when the user lets go of a divider (or presses an arrow key on it), a failure to save shows in the banner, and a tab reads them when it opens (a tab that is already open keeps its own until it is reloaded). Below 800 CSS pixels of width the right column moves under the editor: the editor takes 40% of the height, the issues list and the explanation share the rest (the list's divider still works), and the divider between the editor and the right column is not shown.
- **Toolbar, row 1:** LLM selector (`<select>`), Check button (Cancel while a check runs, section 5.1; disabled while no LLM is selected or the text is empty or only white space), Auto-check checkbox (off by default; Check always works; it shows and saves the `auto_check` setting, announces the change with `settings-changed`, and follows a change made on the options page or in another tab. The pause is `auto_check_delay_s`, section 4.7), Statistics (opens the dialog of section 4.8), Preferences (opens the options page).
- **Toolbar, row 2:** New, Open, Save, Save As, Save to library, Library (section 8). Save, Save As and Save to library are disabled while the text is empty or only white space. Below the row sits the hidden file input of Open (`#file-input`, `accept=".txt,.md,text/plain,text/markdown"`).
- **Legend row:** three category samples (click to hide or show a category, section 4.3), then **Clear** (same as New) and **Copy** (puts the whole text on the clipboard, with its line breaks as `\n`, from the click handler itself because the clipboard needs the user gesture; disabled while the text is empty; the status bar says "Copied" in place of the check state for three seconds, and any redraw of the status bar ends that early). A failed copy is `ClipboardWriteFailed` in the banner.
- **Keyboard:** `Ctrl+Enter` presses Check (or Cancel), `Ctrl+S` and `Ctrl+Shift+S` (also with `Cmd`) press Save and Save As and keep the browser's own "Save Page As" from opening (they do nothing while the button is disabled or a dialog is open), and `F7` / `Shift+F7` move between issues. `Ctrl+N` and `Ctrl+O` stay with the browser. Button tooltips name their shortcut.
- The LLM selector lists the configured LLMs by name, and the last selection is remembered (`selected_llm_id`). When no LLM is selected, or the selected one no longer exists, but some LLMs exist, the page selects the first by name and stores that choice (this is what selects the first LLM that is added on the options page). The page reloads the list on `configs-changed` and the selection on `settings-changed`. With no LLM configured, the selector and Check are disabled, and the explanation panel shows a hint with a link that opens the options page: "No LLM is configured. Add one in Preferences to start checking."
- The status bar shows the check state (`Ready`, `Checking...`, `Check cancelled`, `Check failed`, `N issues` (`1 issue`) / `No errors found`, plus ` · N issues could not be placed`), the word count (`142 words`, `1 word`), and the tokens of the last request and of this tab's session (section 5.8), for example `last: 812 in / 164 out · session: 5.2k in / 1.1k out`, or `last: none · session: 0 in / 0 out` before the first request. `N` counts all issues, hidden categories included. The state goes back to `Ready` when an edit leaves the check with no issue (section 5.5).
- **Tab title**: the text's name and a `*` for unsaved changes, then " – English Tutor". A text without a name shows "Untitled". It follows the name and the flag at once (`TabText`, `src/core/files`). A text has unsaved changes after an edit (typing, pasting, an Alternatives replacement) until it is loaded, saved to a file or saved to the library; a text that is only white space never counts, so it has no `*` and nothing is asked about it.
- **Theme**: light or dark follows `prefers-color-scheme`.
- **Per-tab state.** Each tutor tab has its own text, source, issues, selection, explanation and session token totals. The text, the source key, the name, the library document id, the line ending and the dirty flag are kept in the tab's `sessionStorage` (one JSON value under the key `english-tutor-tab`, version 1, together with the id of the tab that wrote it; `TabPersistence`, `src/tutor/tab-persistence.ts`), so reloading the tab, or restoring a closed tab, gives the text back. It is written 400 ms after a change (not on every key, because a text can be long) and at once when the page is hidden or unloaded; a write the browser refuses (the quota) is logged and the tab goes on. A value that is not exactly what was written (broken JSON, another version, a wrong type, a source that is neither `session:` nor `doc:<id>`) is ignored and the tab starts empty. The editor has `autocomplete="off"`, so that Firefox's own form restoration never competes with this. A restored library text is read again from the library: its title follows the library, and a document that is gone detaches it. Issues are not kept: the text has to be checked again, which counts nothing twice (section 5.7), because the source key is restored. A restored text is a loaded text: nothing is checked by itself. **A duplicated tab** copies `sessionStorage`, so two tabs would share one `session:` source and count a mistake of the same text once. A restored state whose stored tab id differs from this tab's id (the id comes from `tabs.getCurrent()` when the page opens) keeps its text and its name but gets a new `session:` source, and its own tab id is written. A `doc:` source stays, because both tabs then edit the same document (section 13). A state without a tab id (written before this was kept) keeps its source. A tab that the browser restores after it was closed has a new id too, so it also gets a new source, and checking its text again counts its mistakes again.
- **Closing the tab** with unsaved changes asks the browser's own question (`beforeunload`; the page calls `preventDefault`, and writes its state first).
- **Shared data.** The LLM list, the selected LLM, the general settings, the library and the statistics are shared by all tutor tabs and the options page. A page that changes one of them posts a message on the `BroadcastChannel` named `english-tutor` (`configs-changed`, `settings-changed`, `library-changed`, `stats-changed`), and the other pages reload what changed.

### 4.3 Text editor

- A `<textarea>` with a proportional font and word wrap. Underlines are drawn on a mirror layer behind the textarea. The mirror has the same font, padding, width, wrapping and scroll position, and holds the text in transparent colour with the issue ranges wrapped in `<span>`s. The textarea's background is transparent, so the underlines show through. This is how the desktop app's own web version draws them.
- Underline colour and style by category (Okabe-Ito colours; fixed in v1):

  | Category | Colour (light / dark) | CSS `text-decoration-style` |
  |---|---|---|
  | grammar | `#D55E00` / `#FF8A4C` | `wavy` |
  | vocabulary | `#0072B2` / `#56B4E9` | `dashed` |
  | syntax | `#009E73` / `#2FD3A2` | `dotted` |

  `text-decoration-skip-ink: none`, so descenders do not break the line. The mirror never changes the text or the textarea's undo history. The mirror takes the width the textarea's text really has (the room of a scroll bar is taken off), follows its scroll position and size, and ends with a zero-width space so that a text ending in a line break has the same last, empty line. An issue that does not fit the text any more (past its end, empty, overlapping an earlier one) gets no span. The textarea and the mirror share one CSS class for font, padding and wrapping (`src/ui/components.css`).
- The selected issue also has a background of its category colour at about 20% opacity.
- **Selecting an issue from the text.** When the caret moves into an issue's range (click or keys), that issue is selected (section 4.4). The caret is not moved. When the caret moves outside all issues, the selection is cleared and the explanation panel goes idle. The range is half-open: the caret is in an issue from its first character up to, but not including, the position after its last character, so a caret right after a word is outside it, a caret at the start of an issue is inside it (this is where `F7` and a row put the caret), and at the boundary of two touching issues the later one wins. The caret is read from `selectionStart` on `selectionchange`, `keyup`, `mouseup`, `focus` and `select`; only issues of shown categories can be selected. Moving the caret outside also clears a selection that was made from the list.
- **Tooltip.** Hovering an underline shows `<error type label> · <Category>` and, on a second line, the issue's message (for example "Subject-verb agreement · Grammar" / "Use goes."). The character under the mouse is found from the mirror's span rectangles (`getClientRects`; an issue that wraps has one rectangle per line). A hidden category has no tooltip. There is one tooltip element in the page (`role="tooltip"`, not a `title` attribute), shown at once below and to the right of the pointer, moved inside the window when it would not fit, and hidden when the pointer leaves the text or no longer is over an underline, and on a mouse press, a key, the wheel, scrolling, typing, or a change of the issues. While it shows, the textarea's `aria-describedby` names it.
- **Legend.** Clicking a category in the legend hides or shows its underlines and its rows in the list.
- **`F7` / `Shift+F7`** go to the next / previous issue: from the selected issue, or, with none selected, from the caret (next is the first shown issue that starts after the caret, previous the last one that starts before it). They wrap around at the ends and skip hidden categories. The caret goes to the start of the issue, the editor scrolls to it and its row is selected; the keyboard focus stays where it was. The browser's own `F7` (caret browsing) is suppressed on the tutor page.
- Editing moves or removes issues (section 5.5).
- **Right-click menu.** A `contextmenu` listener on the textarea calls `menus.overrideContext({ showDefaults: true })` (the issues list's rows use `showDefaults: false`, section 4.4), so the browser's own entries (Undo, Cut, Copy, Paste, Delete, Select All, spell check) stay, and the extension's two entries are added: **Alternative** and, right below it, **Check** (two entries side by side, not a submenu; the entry for Alternative is not a parent). Firefox lists an extension's entries at the top of the menu, followed by a separator and its own entries (checked in the screenshot harness, which reads the open menu); the page cannot change that. They show only when the textarea has a selection that is not only white space or line breaks (`trimSpace`, as in section 5.10), and not while a manual check runs (the loading layer is up); otherwise the menu is the browser's own. **Alternative** asks for alternatives (section 4.6); with no LLM it opens the panel in its failed state with "No LLM is configured. Add one in Preferences to get alternatives.". **Check** checks the selection (section 5.1) and is disabled while no LLM is configured. The entries are made by each tutor page for itself like the row menu's (section 4.4): `menus.create` with `contexts: ["all"]` and `documentUrlPatterns` matching `tutor.html`, ids that contain the tab id (`editor-alternative-<tabId>`, `editor-check-<tabId>`), created invisible; the page makes them visible (and enables or disables Check) in `menus.onShown` for the menu it opened, calls `menus.refresh()`, and hides them again in `menus.onHidden`. A click is handled only by the tutor page whose tab id matches `menus.onClicked`'s `tab.id`. The selection is read from `selectionStart` / `selectionEnd` (UTF-16 units; a backwards selection has the same two numbers) when the entry is chosen, not when the menu was shown. The code is `src/tutor/editor-menu.ts`.
- **Clipboard.** Copy and Cut put only plain text on the clipboard; a `<textarea>` does this already.
- **Loading screen.** While a manual check runs (Check, `Ctrl+Enter`, the Check menu entry, or a check from a web page), a translucent layer covers the editor with "Checking..." and a busy indicator. The textarea is `readOnly` and the right-click entries are hidden. After 10 seconds the line "We will notify you when the results are ready." appears under the indicator. The layer goes when the check ends in any way, or when a new text is loaded. The Cancel button and the rest of the page stay usable. An auto-check does not show the layer.

### 4.4 Issues list

- A list (`role="listbox"`) at the top of the right column, one row per placed issue, in text order.
- Each row has a category marker in the category colour with a letter (**G**, **V**, **S**). It shows the wrong snippet (cut to about 40 characters) and, on a second line, the error type label and a count badge (`x7`: how often the user made that error type, all time, section 5.7). The badge shows only on the rows of a manual check whose error type has at least one recorded mistake; there is none for issues of an auto-check. The counts are read from the store after each finished check (once its mistakes are recorded), and again whenever another page announces `stats-changed` (the Statistics dialog's reset, Not an error, another tab's check), and the badges are updated in place. Its tooltip is "You have made this mistake 7 times".
- The header reads "Issues (N)", or "Issues (3 of 5 shown)" when hidden categories have issues. The legend is the only filter. Hiding a category also deselects the selected issue if it belongs to it.
- **One shared selection.** The editor and the list select the same issue through one state object (`src/core/issues`). Neither one talks to the other directly.
  - Clicking a row, or Up / Down in the list, selects the issue. The editor scrolls to it (centred when it is out of view), highlights it and puts the caret at its start, without moving keyboard focus out of the list.
  - Selecting an issue in the editor, or with `F7`, selects its row and scrolls it into view (just far enough, without scrolling the page).
  - Selecting an issue from either place starts its explanation (section 5.4).
- Double-clicking a row (or `Enter` on it) moves focus to the editor, with the caret at the start of the issue.
- **Keyboard and ARIA.** The list is one tab stop (`tabindex="0"`, outlined while focused) and keeps the focus; the selected row is its `aria-activedescendant`, and every row has a unique id, `role="option"` and `aria-selected`. Down and Up select the next and previous shown issue (from no selection, Down selects the first and Up the last; they stop at the ends), Home and End the first and last, Enter activates the selected one. Keys with Ctrl, Alt or Meta are left to the browser.
- **A row's context menu** has **Not an error** (the same as the panel's button, section 5.7) and **Regenerate explanation** (selects the row if it is not selected, and asks for a new explanation, skipping the cache; one request). A `contextmenu` event on a row calls `menus.overrideContext({ showDefaults: false })`, so the menu holds only these two entries. The page makes the entries for itself when it loads (`menus.create`, `contexts: ["all"]`, `documentUrlPatterns` = the address of `tutor.html`), with ids that contain its tab id (`row-not-an-error-<tabId>`, `row-regenerate-<tabId>`) so that two tutor tabs do not clash, and removes them when it closes. They are created invisible and are made visible only when the menu this page opened is shown: in `menus.onShown` the page sets them visible (Regenerate explanation disabled while no LLM is selected), calls `menus.refresh()`, and hides them again in `menus.onHidden`. The browser sends menu events to every open extension page, so a click or a shown menu is handled only when its `tab.id` is the id that `tabs.getCurrent()` gave. The row is the one the `contextmenu` event came from, not the selected one. The menus API is behind the `ContextMenus` interface of `src/platform` (with a fake), and the row menu is `src/tutor/row-menu.ts`; the editor's entries (section 4.3) are made the same way. A failure is `ContextMenuFailed`; the page logs it and goes on without the menu.
- Empty states, as one grey line: "Press Check to find errors" (before the first check, and after a first check that failed or was cancelled), "Checking...", "No errors found", and "All categories are hidden" (issues exist but every category is hidden). During a re-check the old rows stay until the result arrives, unless there were none.
- Rows go as soon as an edit removes their issue (section 5.5). Issues the locator could not place are not listed; the status bar counts them.

### 4.5 Explanation panel

- States, as in the desktop app:
  - **Idle:** "Select an error in the list or an underlined error in the text to learn more". (With no LLM configured the idle panel shows the hint of section 4.2 instead.)
  - **Loading:** the header line, the faulty words (as checked) with the category ("He go", "Grammar"), a progress indicator with "Explaining..." and **Cancel**, and below them the text as it streams in (it is the ready layout, drawn while the request runs). **Cancel** shows "Explanation cancelled." and a **Regenerate** button at once; the cancelled request's late result is ignored.
  - **Ready:** the rendered markdown (section 5.9), and **Regenerate**. While it streams, the text is re-rendered at most every 100 ms through the injected `Scheduler`: the first chunk at once, the ones that arrive within the next 100 ms together when that time is over. When the stream ends, the text is rendered once more from the call's final text (section 6.2: a reply with only a closing `</think>` can be cleaned only then). The view follows the end of the text while it grows, unless the user has scrolled up from the end (scrolling back to the end follows again). Following is only for a text that is still arriving: a finished explanation is shown from its top, both a cached one and the one whose stream has just ended while the view followed it. If the user had scrolled up while it streamed, their place stays when it ends. A new request starts at the top.
  - **Failed:** the error's message (in the error colour, role `alert`) and **Retry**.
  - **Cancelled:** "Explanation cancelled." and **Regenerate**.
- Header line: "Subject-verb agreement: you have made this mistake 7 times (2 in the last 7 days)". "1 time" in the singular. With no recorded mistake of the type it reads "<label>: no mistake of this type recorded yet". For an issue of an auto-check the line ends with " This one is not counted: only the Check button counts." after either text ("... (2 in the last 7 days). This one is not counted: only the Check button counts."). The counts are the all-time total and the last 7 days of the issue's error type (`Stats.countForType`), read for the selected issue's type when it is selected and read again after each recording and on `stats-changed`, so a reset in another tab changes the line at once. Until the counts are read, the line is the label alone. The panel only has `setHeaderLine`; `SelectedIssueHeader` (`src/core/issues`) keeps it in step with the selection, and page mode uses the same classes.
- **Not an error** is shown in every state except idle (section 5.7). **Regenerate** shows when the explanation is ready or cancelled, **Retry** when it failed. Its click is handled by the page (section 5.7): the underline and the row go at once, the panel goes idle, and a failure shows in the banner (`StatsResetFailed`) and keeps the issue.
- An explanation is requested only when an issue is selected, by the list, the caret or `F7`. Explanations are cached in memory per issue for the lifetime of the check result: the key is the id of the check that produced the issues (`IssueState.checkId`, 0 before the first result and after a loaded text) and the issue's id. Selecting nothing, removing the selected issue (an edit that touches it, or hiding its category), or a new check result cancels a running explanation and returns the panel to idle. A late result or late text of a cancelled or replaced request is ignored. A new full check result (or a loaded text) clears the cache (`Explainer.reset`); the merged result of a selection check does not (section 5.1). An edit that only moves the selected issue changes nothing: the issue keeps its id.
- Usage of every explanation request is recorded with kind `explain`, also for a cancelled request that reported some (section 5.8).
- If no LLM is configured any more when an issue is selected, the panel shows the failed state with the message "No LLM is configured. Add one in Preferences to get explanations." (plain text: the options link exists only in the idle hint). **Retry** asks again, so it works once an LLM exists.
- **Layout.** The panel fills its host. Its text area scrolls on its own, with the header line, the progress line and the buttons outside the scrolling part. A `compact` layout option (smaller text and padding, buttons that wrap and share the width) is for the page-mode popover of section 4.11, which is about 360 px wide.
- **Links.** Only `http:` and `https:` links with a host are links (section 5.9). A click on one never navigates the tutor page (the default action is cancelled, and so is a middle click): it shows an in-page confirmation, a dialog (`role="alertdialog"`) with the full address as text, **Open link** (focused) and **Cancel**; `Escape` and a click outside the box cancel, and `Tab` stays inside the box. On confirmation the address opens in a new tab right after the tutor tab (`tabs.create({ url, index: current.index + 1 })` with `current` from `tabs.getCurrent()`; neither needs a permission), through the `LinkOpener` interface of `src/platform`, which fails with `LinkOpenFailed` (shown in the banner). Every other scheme is plain text. The options link exists only in the idle hint for a missing LLM, never inside an explanation.

### 4.6 Alternatives panel

As the desktop app's Alternatives window (desktop SPEC §4.2), drawn as a floating, non-modal panel inside the tutor page (`src/ui/alternatives-panel.ts`, behaviour in `src/tutor/alternatives-flow.ts`):

- It sits at the bottom right of the editor, over the editor's text area (not over the issues list or the explanation), `role="dialog"`, `aria-modal="false"`. It shows the selected text (cut to 400 characters, with "…" when cut; code points, never inside a surrogate pair), a state line, and one row per alternative in the model's order (a `listbox`, the selected row `aria-selected`). States: *loading* ("Looking for alternatives..." with a busy indicator), *ready* ("3 alternatives", first row selected, or "No alternatives found."), *failed* ("Could not get alternatives.", the error's message in red, and **Retry**).
- It is opened by the **Alternative** entry of the editor menu (section 4.3) for the selection read at that moment. Focus goes to the panel while loading, to the list when ready and to Retry when failed. `Up`, `Down`, `Home` and `End` move the selected row; a click selects one.
- **Double-click on a row** (or `Enter` in the list) uses it. The panel re-selects the original range and replaces it with `document.execCommand("insertText", false, alternative)`, so the replacement is one step of the textarea's undo history (`Ctrl+Z` brings the old text back, checked in the screenshot harness). The caret goes after it, the panel closes and the editor gets focus. The text is replaced only if the characters at the original range are still the selected ones. Otherwise nothing changes, and the panel says "The text changed, so nothing was replaced. Select it again." under the list and keeps the alternatives (the range is the original one: text typed before it, which moves it, also counts as a change). While a check keeps the editor read-only nothing is replaced either ("The text cannot be changed while a check runs."). If `execCommand` is not available, throws, says no, or leaves the text unchanged, the panel falls back to `setRangeText` and an `input` event of type `insertText`: the edit still reaches the page like typing, but it is not one undo step. The replacement is an edit like typing (section 5.5): the `input` event gives the diff, issues it touches go and later ones move.
- **Copy** puts the current row on the clipboard (`navigator.clipboard.writeText` in the click handler, behind the `Clipboard` interface of `src/platform`; no permission is needed). If that fails the panel says "Could not copy to the clipboard." under the list (`ClipboardWriteFailed`, logged without the text). **Close** (the button or the cross) or `Escape` closes the panel (`Escape` anywhere in the page while it is open, unless something else already handled it). Closing it in any way cancels a running request, and that is not an error: nothing is shown and nothing is logged as an error. A retry after a failure uses the text the first request was made from.
- One panel at a time: asking again replaces it (the text, the state and the note), and the earlier request is cancelled; its late result is ignored.
- Alternatives are untrusted text and are shown with `textContent` only. The panel never changes the statistics. Its requests record usage with kind `alternatives` (and count in the session total of the status bar, not in "last").

### 4.7 Options page (Preferences)

Opened from the Preferences button (`runtime.openOptionsPage()`), from the toolbar button's menu, or from `about:addons`. Changes are saved at once (no OK button) and announced on the `BroadcastChannel`.

**LLMs section.** A list of configured LLMs with Add, Edit, Delete and Test connection. The form fields are the same as in the desktop app (desktop SPEC §4.5):

| Field | Notes |
|---|---|
| Name | Unique, shown in the selector |
| Provider | `ollama`, `openai-compatible`, `anthropic`. A new LLM starts with `openai-compatible` and an empty Base URL |
| Model | Free text, for example `llama3.1`, `gpt-4o`, `claude-sonnet-5-5` |
| Base URL | Required for `ollama` (filled with `http://localhost:11434` when chosen and empty, and cleared again when switching away) and `openai-compatible` (including `/v1`); optional for `anthropic` (default `https://api.anthropic.com`). Must be `http://` or `https://` with a host |
| API key | Required for `anthropic` and usually for `openai-compatible`; disabled and not stored for `ollama`. A password field with Show / Hide, masked when the form opens |
| Temperature | Optional, 0 to 2. Empty (`null`) means the default 0.2, which is always sent |
| Timeout | Optional, seconds, 10 to 3600. Empty or 0 uses the defaults (15 minutes for a check chunk, 120 s for an explanation or alternatives). Test connection ignores it and uses 60 s |
| No thinking | Ticked by default for a new LLM. For `ollama` and `openai-compatible` only (section 6.4); disabled and never stored for `anthropic` |
| Parallel requests | A whole number from 1 to 16, default 1 (section 5.2) |

- **Layout.** The list has the buttons Add, Edit, Delete and Test connection above it; Edit, Delete and Test connection apply to the highlighted row (click, arrow keys; double-click or Enter edits). The LLM used by the editor (`selected_llm_id`) is marked "in use". The form opens below the list, one at a time. Delete asks in an in-page confirmation, not a browser dialog. Validation messages are shown under the field they are about (the first problem takes the focus), and `LLMConfigNameTaken` under Name. Values that fail the form's checks are not sent to the store, and no permission is requested for them.
- **Host permission.** Saving an LLM, or pressing Test connection (in the form or for a row), first calls `permissions.request({ origins: ["<scheme>://<host>[:<port>]/*"] })` for its base URL (the default Anthropic URL for `anthropic` without one). The call is made synchronously in the click handler, before any `await`, because Firefox accepts it only during a user gesture. If the user refuses, the LLM is still saved, and the form stays open (now editing the saved LLM) with a warning that requests to it will fail with `HostPermissionDenied`; pressing Save or Test connection again asks again. The request is made only when the values pass the form's checks. Deleting the last LLM that uses an origin removes that origin's permission (`permissions.remove`).
- **Test connection** sends the desktop app's test prompt ("Reply with the single word: ok") with the typed values (no name needed). It reports success with the time taken, or the failure. The tokens are not counted. A result that arrives after the form was closed is dropped.
- **Privacy note** in the form, as in the desktop app: "the text you write is sent to <server> when you check it, ask for an explanation or ask for alternatives", unless the host is `localhost`, `127.x.x.x` or `[::1]`. For `anthropic` without a base URL it names Anthropic's server. Next to the API key: "API keys are stored unencrypted in your Firefox profile."
- **Ollama note**: Ollama refuses requests from origins it does not allow. A 403 from an `ollama` server gets the message "Ollama refused the request from the extension. Allow it by starting Ollama with OLLAMA_ORIGINS=moz-extension://*." (section 6.5).
- API keys are never shown back in the list, only "key stored". An empty key field in the Edit form keeps the stored key, and a "Remove key" box removes it.
- Deleting the selected LLM selects the first remaining one by name, or none.

**General section.** Auto-check (default off) and its delay in seconds (default 3, 1 to 60; disabled while auto-check is off, unless page mode is offered, which uses it too). Page mode: the box "Offer to check text boxes on websites" with its privacy note ("English Tutor asks on each site before it reads anything there. What you type on a site you turn on is sent to <server> to be checked.", or "... is checked by <server>, on this computer."; the note names the server of the LLM in use, the selected one or the first by name, and follows changes of the LLM list or the selection), and the list of sites with a choice, with their state and a Remove button (section 4.11). Opened as `options.html#welcome`, the page first shows the Welcome block of section 4.11. A font for the editor, the buttons and the results (issues list and explanation): each is a family name typed as text (at most 100 characters; empty means the page's default, a missing font falls back to it) and a size from 6 to 48 points (defaults 13, 11, 11). Family names are applied through CSS custom properties (`--editor-font-family`, `--button-font-family`, `--results-font-family` and the three `-size` ones) set on the page with `style.setProperty`, never by building CSS text (`src/ui/fonts.ts`). A name is put in quotes as a CSS string, with a backslash and a quote escaped and control characters turned into spaces, followed by `system-ui, sans-serif` so that a font that is not installed falls back; a generic family (`serif`, `sans-serif`, `monospace`, ...) stays a keyword. A size is set in points. The tutor page applies them when it opens and again at once on `settings-changed`, so a change on the options page reaches the open tabs. A setting that is empty, or a size equal to its default (13, 11, 11), sets no property and the style sheet decides: the editor and the results already use 13 pt and 11 pt, and the buttons keep the page's own 13 px, which is the look the default button size has. The buttons' font applies to the toolbar (the selector, the buttons, the legend and the labels).

### 4.8 Statistics dialog

As desktop SPEC §4.6, as a modal `<dialog>` in the tutor page with two tabs:

- **Mistakes:** one row per error type with at least one recorded mistake (the counts are `Stats.typeStats`; the dates are the user's local date as `2026-10-30`). Columns: Error type, Category, Total, Last 7 days, Last 30 days, Last seen. Sorted by Total, highest first. Clicking a header sorts by that column: numbers and dates with the largest or newest first, text alphabetically. A second click reverses the order, and ties are ordered by label. A category filter and a period selector (all time, 30 days, 7 days) hide the types with no mistake in that period and drive the summary line ("24 mistakes in all time. Most frequent: Article."; "1 mistake" in the singular; "10 mistakes in the last 30 days" and "... in the last 7 days"; a filtered category in brackets, "20 mistakes in all time (Grammar). ..."; "No mistakes recorded yet." when nothing is recorded and "No mistakes in the last 7 days." when the period is empty). The rows keep the table's sort (Total counts all time, whatever the period); types with the same count are ordered by label in the summary too. Selecting a row (click, or Enter or Space on it) lists its three most recent example snippets with dates; a filter that hides the selected row clears the examples. **Reset statistics** asks for confirmation in the dialog (a red bar with **Delete all mistakes** and **Cancel**, not `window.confirm`), deletes all mistakes, announces `stats-changed`, and so clears the badges and header counts in every tutor tab. The Not-an-error ignore set is not cleared by a reset.
- **Token usage:** one row per LLM with "input in / output out" for all time, 30 days and 7 days. `~` marks sums that include estimates. A row shows the LLM's name at the time of the requests, so a deleted or renamed LLM keeps its row. It has its own **Reset token usage** button with the same kind of confirmation; it also announces `stats-changed`, so that an open dialog in another tab reloads. The dialog reloads on `stats-changed` while it is open.
- A failed query or reset shows its message in a banner inside the dialog (`StatsQueryFailed`, `UsageQueryFailed`, `StatsResetFailed`), not in the page's banner; a tab that cannot be read leaves the other tab usable.

### 4.9 Banner

Failures that are not shown in a panel (a failed check, a file that cannot be opened, a save that failed, an expired hand-off) are shown in a dismissible banner above the editor. A failed check's banner is cleared when the next check starts. The same banner says "The text changed while checking." when a selection check is discarded (section 5.1). `HostPermissionDenied` adds a **Grant access** button to the banner. Its click is a user gesture, so it can call `permissions.request` for the LLM's origin, synchronously in the click handler. If the request is granted the banner goes; if it is refused the banner says "Access was not granted, so English Tutor cannot reach this LLM." The banner is a component (`src/ui/banner.ts`).

### 4.10 Check finished notification

When a manual check ends with a result or a failure while its tutor tab is not visible, or its window is not focused (`document.visibilityState === "hidden"` or `!document.hasFocus()`), the page shows a `notifications` message. It reads "Check finished" with the status text ("3 issues", "No errors found"), or "Check failed" with the error's message. The notification id is `check-<tabId>`, so a second one for the same tab replaces the first. The background script handles `notifications.onClicked`: it asks the tutor pages (section 4.1), focuses the tab and its window (nothing if the tab has been closed since), and clears the notification. A check the user cancelled, a check whose result was discarded, an auto-check, and a check that ends while the tab is visible and focused do not notify.

### 4.11 Text boxes on web pages (page mode)

On the sites where the user turned it on, the extension checks what the user writes in text boxes on web pages, in place, the way it checks the editor page. Underlines appear under the errors inside the text box, a badge on the text box shows how many errors it has, a click on the badge opens a dialog with the issues and their explanations, and a click on an underlined error shows that error's explanation next to it.

```
 +--------------------------------------------------------+
 | Yesterday I seen him. He go to school every day.       |
 |             ~~~~      ~~~~~                            |
 |                  +-------------------------------+     |
 |                  | Subject-verb agreement        |     |
 |                  | "He go" -> "He goes" ...      |  (3)| <- badge
 +------------------| [Not an error] [Regenerate]   |-----+
                    +-------------------------------+
                      explanation popover (click on an underline)
```

**Turning it on.** Page mode is **off on every site by default**, because it sends what the user types to the LLM. It asks on each site before it reads anything there.
- **Access to all websites, asked once.** An extension cannot see which site a tab shows, or show anything in it, without access to that site. So page mode needs the optional `<all_urls>` permission once. When the extension is first installed (`runtime.onInstalled` with reason `install`, not on updates), the background script opens `options.html#welcome`. The tab is opened with `tabs.create` (no permission needed). The options page then shows a **Welcome** block above its sections: a short text on what English Tutor does, **Add an LLM** (opens the Add form of section 4.7), and "Offer to check what you write on websites. English Tutor asks on each site first, and reads nothing on a site until you say yes." with an **Allow** button and a **Not now** button. Not now closes the block and changes nothing. After Allow is granted the offer is replaced by a line saying so, and the General section's box is ticked; a refusal is shown in the block (`PageModePermissionDenied`) and Allow can be pressed again. The fragment is cleared with `history.replaceState`, so a reload does not show the block again. The General section has the same choice as the box "Offer to check text boxes on websites".
- Allow (or ticking the box) calls `permissions.request({ origins: ["<all_urls>"] })` synchronously in the click handler (section 4.7). If the user refuses, the box stays off and the form says so (`PageModePermissionDenied`, with the route `PageModeSection.turnOn->PageModePermissionDenied`; the Welcome block uses the same section code). If it is granted, the options page stores `page_mode = true` and asks the background script to register the content script: `scripting.registerContentScripts([{ id: "page-mode", matches: ["<all_urls>"], js: ["page.js"], runAt: "document_idle", allFrames: true }])`. Unticking the box stores `page_mode = false`, has the background script unregister the script and tell the open pages to remove their prompts, badges and underlines (they listen for a `page-mode-off` `runtime` message), and then removes the `<all_urls>` permission (the pages are told first). The site choices are kept. The options page talks to the background script with the `runtime` message `page-mode-apply`; the background script makes the registration match the setting and the permission and answers when it is done.
- The background script makes the registration match the setting and the permission each time it starts (`runtime.onStartup`, `runtime.onInstalled`) and on `permissions.onRemoved`: if the user withdrew the permission in `about:addons`, page mode is switched off.
- **A site** is the exact host name of the frame the text box is in (`location.hostname`), so `mail.example.com` and `docs.example.com` are asked separately (grouping them by registrable domain would need the public suffix list, which is a dependency). A text box inside an iframe from another host is asked about under the iframe's host. Each site is in one of three states: **on**, **off** (the user chose Never on this site), or **ask** (no choice yet). The choices are stored in `page_mode_sites` (section 9). "Not now" is remembered until the browser restarts, as the key `page-mode-later:<host>` in `storage.session`.
- **The content script on a site it may not read.** The content script cannot read the settings (its IndexedDB is the web page's own), so it asks the background script, with a `runtime` message `page-mode-config` carrying its host name, when it starts and each time it is told `settings-changed`. The answer is the site's state (`on`, `off`, `ask`, or `later` for Not now), and, for `ask`, the server of the LLM in use for the prompt's note (`{ server, local }`: the host and port only, never a key or a path; `null` when no LLM is set up). Page mode that is not offered answers `off`, and so does a host that is not a valid site (a `file:` page has none), or an answer the content script cannot read. On `off` and `later` it does nothing. On `ask` it only listens for the focus: it reads no text and makes no frame.
- **The prompt.** The first time the user focuses a text box that page mode may read (the rules of "Which text boxes" below; never a password, payment or code field) on a site in the `ask` state, a small card opens just below the box (above it when there is no room), in the content script's closed shadow root: "Check what you write on <host> with English Tutor?", the note "What you type here is sent to <server> to be checked." (or "... is checked by <server>, on this computer."; with no LLM yet, "No LLM is set up yet. You can add one in the options."), and three buttons: **Turn on**, **Not now** and **Never on this site**, with a close button that counts as Not now. The card does not take the focus from the text box, and typing in the box does not close it. Its buttons ignore events the page dispatches itself (`isTrusted === false`) and clicks in the first 500 ms after the card appears, so a page cannot click them and the user cannot hit them by accident. The card is 330 CSS pixels wide, follows its text box while the page scrolls or resizes, goes when the box leaves the page, and exists (with its element in the page) only while it is open: a site that is not asked about has no element of page mode at all. The choice is sent to the background script (`runtime` message `page-mode-site` with the host and the choice `on`, `off` or `later`), which takes it only if page mode is offered and the host is the host of the page the message came from (`sender.url`; a content script cannot name another site), stores it and tells the open pages (`settings-changed`). An answer from another tab that makes the site `on`, `off` or `later` closes an open card. The card is shown at most once per page load; a page that is reloaded asks again until the user chooses Turn on or Never.
- **Turn on** makes the site `on` at once: the card closes, the content script starts on the page (a frame and a badge) and takes up the text box the user is in as if it had just been focused, so that it is checked if it has at least 3 words, and its badge appears, without a second click. **Never on this site** makes it `off`, and page mode does nothing more on that page. **Not now** (and the close button) closes the card and the site is not asked again until the browser restarts. Turn on and Never also forget an earlier Not now of the site. A choice stored in `page_mode_sites` wins over Not now.
- **Changing a choice later.** The toolbar button's context menu has **Turn on on <host>** (for a site that is `ask`, `later` or `off`) or **Turn off on <host>** (for a site that is `on`; it makes the site `off`) for the active tab's host. The entry is made hidden with the other entries of the button's menu; the background script gives it its title and shows it in `menus.onShown` (then `menus.refresh()`), only while page mode is offered and the active tab is an `http` or `https` page (its address is visible because `<all_urls>` is granted). The options page lists the sites with a choice, each with its state (On or Off) and a **Remove** button; a removed site is asked again. Changes made on the options page or from the toolbar menu reach the open pages through the background script (`tabs.query({})` and `tabs.sendMessage`, which need no permission), as `page-mode-off` or `settings-changed`.
- Page mode never runs on the extension's own pages, and Firefox does not run content scripts on `about:` pages, `addons.mozilla.org` and other restricted pages.

**Which text boxes.**
- A *text box* is a `<textarea>`, an `<input>` whose type is `text` or missing, or an editing host with `contenteditable="true"` or `"plaintext-only"`.
- These are never read, checked or touched: `<input>` of any other type (password, email, url, search, number, tel, ...); a field whose `autocomplete` is `current-password`, `new-password`, `one-time-code`, `username`, or starts with `cc-`; a `readonly` or `disabled` field; a field with `spellcheck="false"` (code editors and terminals set it); a field inside an element with `data-english-tutor="off"`; and a field that is not visible or is smaller than 40×16 CSS pixels.
- A text box takes part only after the user focuses it, and only on a site that is `on`. Text boxes the user never focuses, and text boxes on a site that is not `on`, are never read.
- A text box is checked only when its text has at least 3 words. A text over 10,000 words is not checked, and its badge says so.

**Checking.**
- Checks start by themselves: when a text box gets the focus with at least 3 words in it and no result for its text yet (a box that is focused again with its result still valid is not checked again), and after the user stops typing for the auto-check delay (`auto_check_delay_s`, section 4.7; the editor's own Auto-check box does not apply here; the frame reads the setting again each time a box is focused). Only the focused text box is checked. As in section 5.1, an automatic check does not cancel a running one (it waits for another pause), and the dialog's manual **Check** replaces a running one.
- Each text box has its own text state, as a tutor tab has (section 5): issues, revision, edit log, selection, and a `session:<uuid>` source made when the box is first focused on that page load.
- Checks that start by themselves are not recorded in the statistics, like an auto-check (section 5.7). The dialog's **Check** button runs a manual check, which is recorded under the box's source.
- Edits move and remove issues as in section 5.5: the content script compares the old and the new text of the box on each `input` event.
- With no LLM configured, the badge shows `!`, and the dialog says so with a link that opens the options page (the frame has no `runtime.openOptionsPage`, so the link asks the background script).

**Badge.** A small round button (22 CSS pixels) at the bottom right inside the focused text box, moving with it (scrolling, resizing, layout changes: scroll and resize events, a `ResizeObserver` on each box and a `MutationObserver`, all repositioning at most once per animation frame, and only once the user has focused a box). It sits inside the box's border and its scroll bar. It shows the extension icon before the first check, a spinner while checking (a ring that stands still when the user asks for reduced motion), the number of issues (in the colour of the category with the most issues, a tie going to the first in the legend, with the count as text so colour is not the only signal), a check mark when there are none, and `!` after a failure, with no LLM, for a text over 10,000 words or when the frame is blocked (its tooltip has the message: the tooltip and the accessible name are also set for the other states). It stays on a text box that has issues after the focus leaves it, and goes when the box's issues are gone or the box leaves the page. An edit moves and removes the badge's issues at once, before the frame answers, with the same rules as the frame's `IssueState` (section 5.5); the frame's answer is used only when it is for the box's current revision. Clicking it opens the dialog (step 16); when the frame is blocked the click shows a small card with the reason and one button, **Open in English Tutor**, which sends the box's text to a new tutor tab (the hand-off of section 4.1, action `check`, right after the page's tab) through a `runtime` message to the background script.

**Underlines.** Drawn over the text box with the colours and styles of section 4.3, never by changing the page's DOM inside the box or its text. They are elements of the content script's closed shadow root (in front of the box, and every one of them has `pointer-events: none`, so typing, clicking and selecting work as if they were not there), made by `src/content/underlines.ts`.
- For a `<textarea>` or `<input>`, a mirror: an element at the box's position with its borders (transparent), padding, size, computed text styles (font, size, line height, letter and word spacing, `white-space`, wrapping, text direction, `text-indent`, `tab-size`, `text-align`, `text-transform`) and its scroll position, holding the text in transparent colour with each issue in a `<span>` (the same nodes as the editor's mirror, section 4.3: `mirrorNodes`, with the end mark). The mirror is as wide as the box's text area really is (`clientWidth`: the room of a scroll bar is taken off) and as high as `clientHeight`, so it wraps where the box wraps, and it clips like the box does. An `<input>` centres its line vertically and does not wrap. Only the spans' underlines are visible: `text-decoration-line: underline`, the category's style, 2 px thick, 3 px below the text, `text-decoration-skip-ink: none`. The spans are set one property at a time through the CSS object model.
- For a `contenteditable` box, the text is read as a string from its text nodes (block elements and `<br>` become `\n`), positions are mapped back to text nodes, and the underlines are drawn along the rectangles of a `Range` over each issue (`getClientRects`), one line per rectangle: an SVG `<path>` (a smooth wave for grammar, dashes, dots) 2 px thick whose bottom is the rectangle's bottom edge, because there is no text of the content script's own to decorate. They are clipped to the box's padding box, so an underline that is scrolled out of the box is not drawn, and an issue with no rectangle in the box has no underline and cannot open the popover.
- **Colours.** The palette is the light or the dark column of section 4.3 by the *page's* backdrop, not by the browser's theme: the first mostly opaque background colour from the box up to the root, dark when its luminance is below 0.45.
- **When it is drawn.** An edit moves or removes the underlines in the same turn as the `input` event (from the content script's own copy of the issues, section 5.5), before the frame answers; each state message of the frame draws them again when it is for the box's current revision; scrolling anywhere, resizing and layout changes draw them at most once per animation frame (the same single frame request that moves the badge). The mirror's content is made again only when the text, the issues, the selected issue or the palette changed; its position, size and scroll are set at each draw. They stay on a box that has issues after the focus leaves it, and go with its issues, when it leaves the page, or while it is out of the window.
- The selected issue (the one the popover shows) gets the 20% background of section 4.3: a `background-color` on its span in a mirror, a rectangle behind its lines for editable content.

**Explanation popover.** When the user clicks inside an underlined error (the caret lands inside an issue, or the click point is inside an issue's rectangles), a card opens just below the underline (above it when there is no room). It has the header of section 4.5 (label and counts), the streamed explanation with its states (loading, ready, failed, cancelled), and the buttons **Not an error**, **Regenerate** / **Retry** and **All issues** (opens the dialog). Moving the caret to another issue switches the card to that issue. `Escape`, a click elsewhere, or typing closes it. It never takes the focus from the text box unless the user clicks into it.
- **What opens it.** A trusted `mouseup` in a box that has issues: the issue whose underline holds the point wins; if there is none, the issue that holds the caret (`selectionStart`, or the start of the selection range in editable content; the range of an issue is half-open as in section 4.3). A keyboard caret never opens it. While it is open, the caret moving (`keyup`, `selectionchange`, `select`) to another issue switches the card, and out of every issue closes it. It also closes on: `Escape` (a trusted `keydown`, anywhere on the page, or in the card), a `mousedown` outside the box and the card, an `input` event in the box (before the underlines are drawn again), the focus going to anything but the box and the card, an edit or a check result that removes its issue, its underline leaving the box, the box leaving the page, and page mode turning off. A new check result gives every issue a new id, so it closes the card too (section 4.5: the explanation returns to idle). A card for a box whose frame is blocked never opens. Events that a page dispatched itself (`isTrusted === false`) do nothing.
- **Who draws what.** The explanation is the LLM's text, so the card is drawn by the frame (`page-ui.html`, `src/page-ui/popover.ts`) with the shared explanation panel in its compact layout and its `ExplanationController`; the content script never holds a word of it. Over the channel (section "How it is built") the content script sends `popover-open { box, issue, maxHeight }` and `popover-close { box }`; the frame answers `popover-size { box, issue, height }` (the card's height, again whenever it changes), `popover-closed { box }` (Escape in the card, Not an error, an issue that is gone) and `all-issues { box }`. Opening selects the issue in the box's `IssueState` in the frame, which starts the explanation and fills the header with the counts of the issue's type (read from the store, not recorded for an issue of an automatic check); each box has its own `Explainer`, so its cache lives as long as the check result (section 4.5). Closing deselects, cancels the running request and hides the card.
- **How the frame is shown, sized and placed.** The content script alone decides: the same `<iframe>` that runs the checks becomes the card, as a `position: fixed` element of the closed shadow root with every property `!important`, so no page style can move, resize, hide or restyle it, and the page has no way to reach into the root or into the extension frame (a different origin). It is 360 CSS pixels wide (narrower in a narrow window), as high as the card the frame reports (at most 340, and at most the room there is: the larger of the space below and above the underline, at least 140; the frame gets that number as `maxHeight` and scrolls the explanation inside it), with a corner radius of 8 px and a shadow. Its left edge is the left edge of the underline (of the line that was clicked, for an issue that wraps), moved to stay 8 px inside the window; its top is 6 px below the underline, or, when the card does not fit below, 6 px above it (`placePopover`, `src/content/popover-place.ts`; when it fits on neither side it goes on the side with more room and is cut to it). It stays `visibility: hidden` and out of the pointer's way until the frame has reported the size of the card for the current issue, and is `display: none` when closed. It is the only thing of page mode that takes the pointer, so a click on the card never reaches the page, and a click in the page never reaches the card. It follows its underline while the page scrolls or resizes (the frame request of the underlines). Clicks and keys reach the frame only from the user: events cannot be forged into another origin's document.
- **Focus.** A press on one of the card's buttons is cancelled in the frame (`mousedown` default prevented), so the text box keeps its focus; a press on the explanation's text may focus the card, as the user asked. While the focus is in the card the box counts as still being used: the popover stays open, and `Escape` in the card closes it and gives the box its focus back. The card's keyboard order is the explanation's text, the links in it, Not an error, Regenerate / Retry, All issues.
- **Not an error** is section 5.7 for the box's `session:<uuid>` source: the pair goes into the ignore set, the issue and its underline go at once and the card closes, and `stats-changed` is announced. The frame has no `storage.session` (checked in Firefox 159: `browser.storage.session` is `undefined` in an extension frame inside a web page), so the ignore set is reached through the background script (`runtime` message `page-mode-ignore` with `has`, `add` or `move` and the source and fingerprint, answered only for the extension's own code in a tab, `src/platform/ignore-set.ts` `RuntimeIgnoreSet`), which keeps the same `ignore:<source>|<fingerprint>` keys in `storage.session`. A failure (`StatsResetFailed`) shows in the card in the error colour and keeps the issue.
- **Links** in the explanation ask first, as in section 4.5, but inside the card (the card grows to hold the question); on Open link the frame opens the address with `window.open(url, "_blank", "noopener,noreferrer")` (it has no `tabs`; the click is the user's gesture, so it is not a pop-up) (`WindowLinkOpener`).
- **All issues** is a stub until step 16: the frame sends `all-issues` and the content script calls its `onAllIssues` seam; nothing is shown, and the card stays.

**Issues dialog.** Opened from the badge, or from All issues in the popover. A panel of about 440×520 CSS pixels next to the text box (inside the viewport), with the issues list of section 4.4 on top and the explanation panel of section 4.5 below it, for the issue selected in the list. Selecting a row highlights that issue in the text box and scrolls it into view, without moving the caret. It also has **Check** (a recorded manual check, Cancel while it runs), **Open in English Tutor** (sends the box's text to a new tutor tab with the hand-off of section 4.1; nothing is written back), and **Close** (`Escape`). The legend toggles of section 4.3 are not part of page mode.

**How it is built.**
- The content script (`src/content/`) finds text boxes, keeps their text states, and draws the badge and the underlines. Everything it adds to the page lives in one element (a `div` directly in `<html>`) whose closed shadow root holds the badge, the overlays and the frame, with `all: initial` and `!important` on every property, so the page's styles cannot change it and it cannot change the page. Its styles are set one property at a time through the CSS object model and its animations use the Web Animations API, so that a strict `style-src` cannot stop them; it draws the badge's icon with `createElementNS`. It never uses `innerHTML`, and never trusts the page: it reads only the text boxes it is about, and it ignores events the page dispatches itself (`event.isTrusted === false`). It never answers a `runtime` message (the tutor pings are for the tutor pages).
- The popover and the dialog are one extension page, `page-ui.html` (`src/page-ui/`), loaded in an `<iframe>` inside that shadow root. It is listed in `web_accessible_resources` for `<all_urls>`. It is an extension context in the extension's origin, so it uses the same IndexedDB (not partitioned by the web page, checked in Firefox 159), LLM clients, analysis code and UI components as the tutor page. **An extension frame inside a web page has only a few of the extension APIs** (`runtime`, `storage` without `storage.session`, `menus`, `i18n`; checked in Firefox 159): not `permissions`, not `tabs`, and `browser.storage.session` is `undefined`, so what lives there (the ignore set) is reached through the background script. The frame therefore treats the host permission of an LLM as granted (`src/page-ui/permissions.ts`): it exists only while page mode is on, which needs `<all_urls>`, and that covers every origin; if the user withdraws it, the background script switches page mode off and the page removes the frame. The frame is created, hidden, when the first text box is focused; it runs the checks and the explanations of that page, and it is shown, as the card of the popover (and later the dialog), by the content script alone (one frame per page frame that has a focused text box). The page cannot read the frame, and the content script never receives API keys or makes LLM requests.
- **The content script and its frame talk over a `MessageChannel`**, not over `runtime.connect`: in Firefox 159 a content script's `runtime.connect` and `runtime.sendMessage` are not delivered to an extension frame inside a web page (the frame's `runtime.onConnect` and `runtime.onMessage` never fire, while the frame's own messages reach the background script). The content script makes the channel, gives its second end to the frame with `postMessage` to the frame's window addressed to the extension's origin (`moz-extension://<uuid>`, so only the frame receives it), and the message names the frame by a random id (a UUID from `crypto.getRandomValues`) that is also the fragment of the frame's address. The frame accepts exactly one port, the one offered with its own id (`src/platform/page-port.ts`, `src/core/page-mode/protocol.ts`); a port offered with another id, or a second one, is ignored. **The id alone proves nothing**, because the id is in the frame's own address, and a web page can make an `<iframe>` of `page-ui.html` itself, choosing the fragment and the port's id. So the id is also registered with the background script (`src/core/page-mode/frame-claims.ts`). Before it makes the iframe, the content script sends `runtime.sendMessage({ type: "page-frame-register", id })`; the background script stores `page-frame:<id>` → `{ tabId, at }` in `storage.session`, with the `tabId` of the message's sender (the browser fills it in, and a page's script cannot send `runtime` messages). When the frame is offered a port with its own id it does not answer `ready` yet: it sends `{ type: "page-frame-claim", id }`, and the background script grants it only when the entry exists, is not older than 5 minutes, and its `tabId` equals the claim's sender tab (the frame's `sender.tab` is set and is the tab of the web page that contains it, checked in Firefox 159). The entry is deleted by every claim, granted or not, so an id is claimed once. A refused or failed claim makes the frame disconnect the port and do nothing (the content script's 5-second timer, or the disconnect, ends in `PageFrameBlocked`; a failed registration is `PageFrameBlocked` at once). Entries nobody claimed are deleted when the background script starts, like the hand-off entries. A frame that a page makes by itself has an id nobody registered, so it never starts, and the page cannot use the user's LLM through it (the screenshot harness has the scenario `page-made-frame`, which also shows that without the claim the page's frame would answer). The page's scripts cannot see the channel. Messages carry the box's id, the revision and the text (once, when the box is focused) or the edits (start, removed length and inserted text) from the content script, and the issues (id, range and category) with the badge state from the frame (`idle`, `checking`, `checked`, `failed`, `no-llm`, `too-long`, with a message for the last three); the popover adds `popover-open` and `popover-close` (content script to frame) and `popover-size`, `popover-closed` and `all-issues` (frame to content script), described under the explanation popover. A gap in the revisions makes the frame ask for the whole text again (`resync`). Every message is checked on arrival.
- If the frame does not answer within 5 seconds, the badge shows `!` with `PageFrameBlocked` ("This site does not let English Tutor show its panel"), and its click offers only Open in English Tutor. The content script waits for the frame's `ready` message over the channel (the frame's `load` event alone does not say that its script runs). In Firefox 159 a page's `Content-Security-Policy: frame-src 'none'` and `Cross-Origin-Embedder-Policy: require-corp` do **not** stop the frame (loads that a content script starts for the extension's own resource are not subject to the page's `frame-src`); a `Content-Security-Policy: sandbox` does (the frame inherits the page's sandbox flags, so its script cannot run), and so would any other reason why the frame never answers. The screenshot harness has both pages (`strict-csp.html` works, `blocked-frame.html` is blocked).
- **Shared UI.** The issues list (section 4.4) and the explanation panel (section 4.5) are components in `src/ui/` that both the tutor page and `page-ui.html` use.

## 5. Error analysis

The rules of this section are those of desktop SPEC §5, ported to TypeScript in `src/core/analysis` and `src/core/issues`. Positions are UTF-16 code units everywhere. JavaScript strings are UTF-16, so offsets need no conversion: the desktop app's `UTF16Map` and byte offsets have no equivalent. A character above U+FFFF is two units, as in the desktop app. No offset the analysis code returns falls inside a surrogate pair, and the limits "in characters" below count code points. The reference's rules about white space, letters and digits and lower-casing are kept on JavaScript strings: white space is Go's `unicode.IsSpace` (which includes U+0085 and U+00A0 but not U+FEFF), a word character is a Unicode letter or decimal digit, and lower-casing is done one code point at a time (so that the same snippet lower-cases the same wherever it stands; U+0130 becomes `i`).

### 5.1 Pipeline

1. The user presses Check (or auto-check fires, or a check comes from a web page).
2. The page snapshots the text and a revision counter, and sends the check prompt to the selected LLM.
3. The LLM answers with JSON issues. The page parses them (section 5.2), places each one in the snapshot (section 5.3), and drops the ones it cannot place.
4. If the text is at the same revision, the issues replace the underlines. Otherwise they are rebased across the edits made meanwhile (section 5.5).

- One check runs at a time per tutor tab. A new check cancels the previous one through its `AbortController`.
- A check started by the user (Check button, `Ctrl+Enter`, the Check menu entry, a web page's "Check with English Tutor") is *manual* and records its mistakes (section 5.7). An auto-check is not recorded.
- **Auto-check** (off by default): a debounce timer restarts on every edit and starts a check after the configured pause (`auto_check_delay_s`, read each time the timer restarts). If it fires while a check runs, it does not cancel that check: it waits for another full pause and tries again, until no check runs, so that text typed during a long check is checked afterwards. It starts nothing when auto-check is off (turning it off also stops the wait), when no LLM is selected, or when the text is blank. An auto-check is not recorded, shows no loading layer and does not make the editor read-only. Its issues keep the flag `manual: false` (`TextIssue.manual`), so that they get no count badge (section 4.4) and are not counted (section 5.7).
- **Cancel:** while a check runs, Check becomes Cancel. A cancelled check leaves the issues and the recorded mistakes as they were, discards chunks that already finished, shows "Check cancelled" without a banner, and creates no error tag. Cancelling is recognised from the `AbortSignal` before a failure is turned into an error. A timeout is not a cancel and gives `LLMCallTimeout`.
- **Checking a selection** (the **Check** entry of the editor menu, section 4.3): only the selected text is sent. It is a manual check: the loading layer shows, the editor is read-only, the result is recorded (section 5.7) and Check becomes Cancel. `Analyzer.check` takes the selection's offset and the whole text; the placed issues' offsets are shifted back into the whole text, and each placed issue carries its fingerprint (section 5.7) computed in the whole text, so it is that of a full check and nothing counts twice. A range that is outside the text or only white space fails with `SelectionEmpty` before anything is sent.
  - **Merge.** When the result arrives, the issues that overlap the selection (`issue.start < selection.end` and `issue.end > selection.start`; an issue that only touches it stays) are replaced by the new ones, which have new ids, and all other issues stay as they are, ids included. The list is kept in text order. A selected issue outside the selection stays selected, one inside it is deselected. The *not placed* count becomes the selection's (it is not added to the earlier one). The check counts as finished (status `N issues`). Edits made during the check are applied as for a full check (section 5.5), and the selection's range moves with the edits before it.
  - **Explanations and `checkId`.** `IssueState.checkId`, the key of the explanation cache (section 4.5), is the id of the check that produced the result. A merged result keeps it when an earlier result exists: the issues that stay keep their ids, so their cached explanations stay valid, and the new issues have new ids so nothing collides. It takes the selection check's own id only when there was no result before (nothing checked, or every issue gone after edits, or a loaded text). So a selected issue outside the selection keeps its explanation, and the explanation of one inside it goes with the issue (the selection is cleared and the panel is idle). The cache is not emptied; entries of replaced issues stay in memory until the next full result.
  - **Touched selection.** If an edit made during the check touched the selection's range (the test of section 5.5 applied to the range, after the earlier edits moved it), the result is discarded and the banner (section 4.9) shows "The text changed while checking." The issues stay as they were, nothing is recorded, and the outcome is `stale` with the reason `selection-edited`. Other discarded results (a newer check, a loaded text, an overflowed log) show nothing. An edit before or after the selection does not discard it.
  - **Cancel** leaves the issues, the selection of an issue, the recorded mistakes and the explanation as they were ("Check cancelled", no banner).
- A failed check shows its message in the banner and keeps the old issues.
- **Check controller.** One `CheckController` per text (`src/core/issues`, no page dependencies; the tutor page has one, and page mode will have one per text box) takes the snapshot of the text and the revision, runs the check through the analyzer, tells manual from automatic, and puts the result into the text's `IssueState`. It ends as `finished`, `cancelled`, `failed`, `stale` (a newer check replaced this one, or the text changed while checking and the result cannot be applied), `busy` (an auto-check was refused because a check runs) or `no-llm`. A manual check replaces a running one; the older one ends `stale` and does not touch the state. A result applies only if its check is still the pending one. If the text was edited meanwhile, the result is rebased across the edits the state logged (section 5.5) and then applied; it is `stale` (and the state keeps the issues it had) only when the edit log overflowed, a text was loaded meanwhile, or an edit touched the range of a selection check.

### 5.2 Check prompt and reply

As desktop SPEC §5.2:

- The system prompt and the retry reminder are those of `internal/analysis/prompt.go`. They include the taxonomy ids (section 5.6) and the delimiter lines with a random per-request token. The token is 26 random base32 characters from `crypto.getRandomValues`, drawn again while the text contains it.
- Reply contract: `{"issues": [{"text", "error_type", "message", "context_before", "context_after"}]}`. The model never gives offsets.
- Parsing is tolerant about packaging and strict about content. Markdown fences and prose around the JSON are ignored, and so is text before a closing `</think>`. A bare JSON array of issues is accepted. Without an `issues` list the reply is invalid. The JSON is decoded as the desktop app's decoder does: the first value that starts at a `{` (the first 8 are tried) is read and what follows it is ignored, member names match in any case, and a field of the wrong type (a number for `text`, an entry that is not an object) makes that object invalid, while `null` counts as empty. Entries without `text` are dropped and counted. `message` is cut at 300 characters and the contexts at 200 (`context_before` keeps its end, the others their start). A snippet over 2000 characters is dropped. An empty `message` becomes the error type's label.
- An invalid reply is retried once with the reminder appended, then fails with `LLMResponseInvalid`. The error carries only the reply's length (`reply_length`) and the stop reason (`stop_reason`), never the reply. A stop reason of `length` or `max_tokens` changes the message to say the answer was cut off, and suggests a shorter text or more parallel requests.
- **Chunking** (`SplitChunks`): at most 2000 words per request, cut at paragraph boundaries where possible, then between sentences, then between words. The chunks are contiguous, and whitespace stays with the text before it. With *Parallel requests* above 1, chunks are `ceil(words / parallel)` words, at least 200 and at most 2000. At most *Parallel requests* chunks are in flight at once. The results are merged in text order, whatever order they finished in. The first chunk that fails cancels the others, and its error is reported.

### 5.3 Locating issues

As desktop SPEC §5.3, on JavaScript strings:

1. Find all occurrences of `text` (overlapping ones too). Exactly one: use it.
2. Several: prefer those that do not start or end inside a word. Then prefer the one whose neighbours best match `context_before` / `context_after` (ignoring whitespace at the contexts' edges). Then take the first one not claimed by another issue.
3. None: retry case-insensitively, treating any run of whitespace as one space and typographic quotes (`‘ ’ “ ”`) and dashes (`– — −`) as plain ones. Map the match back to offsets in the original text. Otherwise drop the issue and count it.
4. Overlapping issues: keep the earlier one, drop the later one.

The result lists the placed issues in text order, and two counts: *not placed* (issues whose snippet is not in the text, plus the entries the parser dropped; this is the count the page shows) and *overlapping* (issues dropped by step 4). A match never starts or ends inside a surrogate pair, so a snippet that is half an emoji is not placed.

### 5.4 Explanation request

As desktop SPEC §5.4: the system prompt of `internal/analysis/explain.go`, asking for markdown with **What is wrong**, **Why**, **Better ways** and **Remember**. The snippet is taken from the checked text at the issue's offsets. The context is the whole text up to 600 words, otherwise the paragraph around the issue cut to a 600-word chunk. Both are delimited as in the check prompt. The reply is streamed (section 6.2). One explanation runs at a time per tab. The cache key is the check id and the issue id. An empty answer is `LLMResponseInvalid`. The cache is in the explainer, keyed by a string the page gives (the key above) and emptied by `reset()` when a new check result replaces the old one; starting an explanation, or reading a cached one, cancels the running one. The snippet in the prompt is taken from the text at the issue's offsets, or from the model's `text` when the offsets do not fit the text.

### 5.5 Edits after a check

The textarea's `input` event gives the new text. The edit is found as the part between the common prefix and the common suffix of the old and new text: position, removed length, added length, in UTF-16 units (an edit never starts or ends inside a surrogate pair). The page applies it to the issue state before anything redraws. All of this is in `src/core/issues` (`edits.ts`, `TrackedText`), with no DOM, so that page mode uses it for each text box. Then, as desktop SPEC §5.5:

- An edit that ends strictly before an issue's start shifts the issue by the net length change.
- An edit that touches the issue removes it at once (underline and row). It touches when it ends at or after the issue's start and starts at or before its end, so typing right after a word counts.
- An edit that starts strictly after an issue's end leaves the issue alone.
- Touched issues are removed from the state, the list and the mirror in the same turn as the edit. If the removed issue was selected, the selection is cleared; a selected issue that only moved stays selected. The snippet of a kept issue stays the text that was checked (it is what the statistics use). The *not placed* count stays while issues remain.
- When an edit leaves no issue, the check no longer says anything about the text: the status goes back to `Ready` and the list to "Press Check to find errors" (also after "No errors found").
- Edits made while a check runs are logged (at most 100,000) in the order they happen; the log starts when the check starts (and so carries its revision). The result is rebased across them in order, and touched issues are dropped. If the log overflowed, or a text was loaded meanwhile (which is not an edit and cannot be rebased), the result is discarded and the old issues stay. A result of a check that is no longer the pending one is ignored.
- Loading a text (New, Open, a library document, a hand-off) is not an edit. It clears the issues, cancels a running check or explanation, and does not start an auto-check.

### 5.6 Error type taxonomy

The fixed list of `internal/analysis/taxonomy.go`, with the same ids, labels and categories:

| Category | Error types (id) |
|---|---|
| grammar | `subject_verb_agreement`, `verb_tense`, `verb_form`, `modal_verb`, `article`, `preposition`, `plural_singular`, `countable_uncountable`, `pronoun`, `comparative_superlative`, `grammar_other` |
| syntax | `word_order`, `missing_word`, `extra_word`, `sentence_fragment`, `run_on_sentence`, `conditional_structure`, `syntax_other` |
| vocabulary | `wrong_word`, `confused_words`, `collocation`, `spelling`, `vocabulary_other` |

An unknown `error_type` becomes the `_other` id of the category its wording suggests, or `grammar_other`. Punctuation and capitalisation are `syntax_other`. The database stores ids as text, so adding an id needs no migration.

### 5.7 Counting mistakes

As desktop SPEC §5.7:

- A **mistake** is a placed issue of a manual check, stored as an event: error type, category, snippet, source key, fingerprint, LLM name, time.
- **Fingerprint:** hex SHA-256 (`crypto.subtle.digest`) of `normalise(snippet) + "\u0000" + occurrence`. `normalise` lowercases the snippet and collapses every run of whitespace to one space, trimming the ends. `occurrence` is the number of non-overlapping occurrences of the lowercased snippet in the lowercased text before the snippet's start, in decimal. The function is asynchronous (`crypto.subtle`); offsets that do not fit the text are clamped into it. The pair (`source_key`, `fingerprint`) is unique, and inserting an existing pair does nothing. If a later check gives the same mistake another type, the first type stays.
- **Sources:**
  - `session:<uuid>` (a random version 4 UUID from the injected `Random.uuid()`, which is `crypto.getRandomValues` underneath, so tests can make it predictable) for a new text: at New, at the first load of a tab, for an opened file, for a hand-off from a web page, and for each page-mode text box when it is first focused on a page load (section 4.11);
  - `doc:<id>` for a library document.

  There is no `file:` source, because the browser gives no file path. Opening the same file twice counts its mistakes twice (section 13).
- The tab's source is a `TabSource` (`src/core/store/source.ts`): made when the tutor tab loads (or restored from the tab's `sessionStorage`), renewed at New, Clear and Open, set to `doc:<id>` when a library document is opened, and moved to `doc:<id>` by Save to library.
- **Moving a source:** Save to library on a text that is not (or no longer) a library document moves the events of its current source (`session:<uuid>`, or the `doc:<old id>` of a document that was deleted) to the new `doc:<id>` (`Stats.moveSource`, which resolves with how many were moved and dropped), dropping events whose pair would become a duplicate, and moves the source's Not-an-error pairs too, so a re-check of the saved text does not record again what was marked as not an error. A failed move (`ErrorEventSaveFailed`) is shown in the banner; the document is stored and the text is attached to it anyway. Downloading a file (Save, Save As) does not change the source. A manual check records under the source the tab has when the check ends, so a Save to library made while it runs does not leave its mistakes under the old key.
- Repeated mistakes count every time they are made, in different texts or twice in one text. Fixing a mistake does not remove its count.
- **Only manual checks are recorded**, by the tutor page after the issues are placed (`CheckController`'s `finished` outcome with `manual`), under the tab's source and with the LLM's name, for every placed issue of the result (also one that an edit made while the check ran has since removed). A selection check records the placed issues of its result, which are the ones inside the selection. A failed recording (`ErrorEventSaveFailed`) shows its message in the banner and leaves the underlines and rows as they are. Nothing is announced when nothing was inserted; otherwise `stats-changed` goes out, and the badges and header counts are read again.
- **Not an error** deletes the issue's event and adds its (source, fingerprint) to an ignore set kept in `storage.session`, shared by all tutor tabs until the browser closes, so a re-check does not record it again. It is done for the selected issue by the panel's button and for any row by the row's menu. It works for an issue of an auto-check too (there is no event to delete; the pair is still ignored). Page mode's popover does it for the box's `session:<uuid>` source (section 4.11): its frame has no `storage.session`, so `src/platform/ignore-set.ts` has a second implementation, `RuntimeIgnoreSet`, that asks the background script to keep the same keys. The pair is one `storage.session` key per pair (`ignore:<source>|<fingerprint>`), so two tabs adding pairs at the same moment cannot overwrite each other; the set is behind the `IgnoreSet` interface of `src/core/store` and `src/platform/ignore-set.ts` implements it over the `SessionStorage` wrapper (`src/platform/session-storage.ts`, with a fake).
- The `store.Stats` API mirrors the desktop app's: `record` (reports inserted, duplicate and ignored; a duplicate pair does nothing and keeps the first type, time and LLM name), `notAnError`, `moveSource`, `typeStats` (all-time, 30-day and 7-day counts, category and last seen per type, only for types with a mistake), `countForType` (total, 30 days, 7 days), `recentExamples` (newest first, three by default), `summarize` (mistakes in a period and the most frequent type), `resetMistakes`, and for token usage `usageTotals` (per LLM: all, 30 days and 7 days, with the estimated flag) and `resetUsage`. A window is "now minus 7 (or 30) days, inclusive" (a mistake exactly 7 days old counts, one that is a millisecond older does not). Time comes from the injected clock. `typeStats` and `countForType` read only the keys of the `error_type_created_at` index (`[type, created_at]`) and `count()` ranges, not the records. Failures: `record` and `moveSource` are `ErrorEventSaveFailed`, the reads `StatsQueryFailed` (`UsageQueryFailed` for `usageTotals`), `notAnError`, `resetMistakes` and `resetUsage` `StatsResetFailed`, each with the route `Stats.<method>-><Tag>` (section 10). A failing ignore set is the failure of the method that used it.

### 5.8 Token usage

- Every LLM request (each check chunk with its retry, each explanation, each alternatives request) records input and output tokens. Test connection is excluded. A cancelled or failed request records what it reported, and nothing if it reported nothing: a streamed explanation records the usage it had reported when it stopped, and a check chunk or alternatives request that was cancelled or failed after a first reply records that reply's usage. A check chunk and its retry are one record, as are the two requests of an alternatives retry. The analysis code hands each record (`{ llm, kind, usage }`) to an injected recorder; the store implements it (`StoreUsageRecorder`), and a recorder that fails is logged and never fails the request.
- Usage is read from each wire format (section 6.3) into `{ inputTokens, outputTokens, estimated }`. If the provider reports none, or only zeros, both are estimated at about 4 characters per token and `estimated` is true. The page marks estimates with `~`.
- The status bar shows the last request (the whole check, all chunks and retries) and the tab's session totals: `last: 812 in / 164 out · session: 5.2k in / 1.1k out`. Counts from 1000 on read `1.2k` and from a million `3.4M`; an estimate has `~` before each number (`~812 in / ~164 out`). Session totals start at zero when the tab is opened. The session total adds every recorded request, whatever its outcome; the last request is the tokens of the last check that ended with a result or was cancelled (a check that failed has no tokens to show, so the previous value stays).
- Each request is stored in `llm_usage` (LLM name, kind `check` / `explain` / `alternatives`, tokens, estimated flag, time) for the Token usage tab, by `Store.recordUsage` (the `StoreUsageRecorder` is the analyzer's `UsageRecorder`). A write that fails is `UsageSaveFailed` with the route `Store.recordUsage->UsageSaveFailed`; it is logged and the request's result is still shown. `Stats.usageTotals` sums the rows per LLM name for the Token usage tab (all time, 30 days, 7 days; the sum is an estimate, `~`, when any of its rows is), and `Stats.resetUsage` deletes them (section 4.8). No money amounts are shown.

### 5.9 Untrusted text and output

The LLMs have no tools, so text in an essay can change only the model's answer. The measures keep the answers usable and the page safe:

- The user's text is delimited with a random per-request token (section 5.2) and declared to be text to analyse, never instructions.
- Replies are validated: the JSON contract, snippets that must be found in the text, unknown types mapped to `_other`.
- **Markdown renderer** (`src/core/markdown`): a port of the desktop app's `internal/web/markdown.go` rules that produces DOM nodes (a `DocumentFragment` made with an injected `document`, so it works in a page frame and in tests), never HTML text. It supports paragraphs (a soft line break is a space; a hard break, two trailing spaces or a trailing backslash, is a `<br>`), headings, bold, italic, inline code, fenced and indented code blocks, ordered and unordered lists, block quotes and links. A heading `#` is an `h3` and deeper ones follow, capped at `h6` (the panel has its own header line above); a `###` heading is an `h5`. Lists may have a blank line between items (it is one list), and a more indented line continues the item above it; there are no nested lists. A line of `---` is plain text (no `hr`). Raw HTML is shown as text. An image is shown as its alt text and is never fetched. Nested emphasis and quotes stop at a fixed depth and are shown as text beyond it. A link is made only when its target is an absolute `http` / `https` address with a host (no user name or password, no control characters or spaces, at most 2,048 characters); the `href` is the normalised address (`URL.href`). Text inside a link is never a second link. A link opens through the confirmation of section 4.5. The only elements it may create are `p h1-h6 strong em code pre ul ol li blockquote a br`, and the only attributes are `href`, `target="_blank"` and `rel="noopener noreferrer nofollow"` on `a` (a fallback so that a click that escapes the page's handler still never navigates the tutor page); the page adds its click handling by event delegation, not by attributes. A randomised property test (seeded) feeds it arbitrary input, markdown and HTML-like fragments included, and checks that nothing else appears and that nothing throws.
- Alternatives and issue messages are shown with `textContent` only.
- No page uses `innerHTML` or its relatives (CLAUDE.md), and the extension CSP forbids inline and remote scripts.

### 5.10 Alternatives

As desktop SPEC §5.10: the system prompt of `internal/analysis/alternatives.go` (3 to 5 alternatives, each a replacement for the whole selection), delimited like the check prompt, with the context rule of section 5.4. The reply is `{"alternatives": [...]}`, or a bare array of strings. Entries are trimmed. Empty entries, repeats and the selection itself (ignoring case) are dropped, at most 8 are kept, and entries over 6000 characters are dropped. An invalid reply is retried once, then fails with `LLMResponseInvalid`. An empty or white-space selection is `SelectionEmpty`, and over 600 words is `SelectionTooLong`; neither reaches the model. Not streamed. Timeout 120 s or the LLM's Timeout. One request at a time per tab. Usage is recorded with kind `alternatives`, the retry included in the same record.

## 6. LLM providers

`src/core/llm` talks to the three providers with `fetch` from the tutor and options pages, never from the background script (an event page can be stopped while a long request runs). Each client takes the page's `fetch`, so tests can replace it. All requests send `Content-Type: application/json`.

### 6.1 Requests

| Provider | Endpoint | Body | Headers |
|---|---|---|---|
| `ollama` | `POST {base}/api/chat` | `model`, `messages` (system, user), `stream`, `options.temperature` | none |
| `openai-compatible` | `POST {base}/chat/completions` | `model`, `messages`, `temperature`, `stream`, and `stream_options: {"include_usage": true}` when streaming | `Authorization: Bearer <key>` when a key is set |
| `anthropic` | `POST {base or https://api.anthropic.com}/v1/messages` | `model`, `system`, `messages` (user), `max_tokens`, `temperature`, `stream` | `x-api-key`, `anthropic-version: 2023-06-01`, `anthropic-dangerous-direct-browser-access: true` |

- `max_tokens` (Anthropic only, which requires it) is 8192 for a check chunk and 4096 for an explanation or alternatives.
- A trailing `/` of a base URL is removed before the path is appended.
- Checks and alternatives are sent without streaming. Explanations stream.

### 6.2 Streaming

- `ollama`: newline-delimited JSON objects; the text is `message.content`, and the last object has `done: true`.
- `openai-compatible`: Server-Sent Events, `data: {json}` lines ending with `data: [DONE]`; the text is `choices[0].delta.content`.
- `anthropic`: Server-Sent Events. The text comes from `content_block_delta` events with a `text_delta`, and the stream ends with `message_stop`. An `error` event fails the request.
- The parsers read `response.body` with a `TextDecoderStream` and handle lines split across chunks. Thinking output is never shown: Ollama's `message.thinking`, an OpenAI-compatible `reasoning_content`, and text before a closing `</think>`. While streaming, a reply that starts with `<think>` is held back up to `</think>`; a reply with only a closing tag cannot be known to be thinking until the tag arrives, so it is shown as it comes and is removed from the final text the call returns (the text of an explanation is re-rendered from that final text).

### 6.3 Usage and stop reason

| Provider | Input tokens | Output tokens | Stop reason |
|---|---|---|---|
| `ollama` | `prompt_eval_count` | `eval_count` | `done_reason` |
| `openai-compatible` | `usage.prompt_tokens` | `usage.completion_tokens` | `choices[0].finish_reason` |
| `anthropic` | `usage.input_tokens` (stream: `message_start`) | `usage.output_tokens` (stream: last `message_delta`) | `stop_reason` |

### 6.4 No thinking

As desktop SPEC §4.5: fields are added at the top level of the body, keeping any field the body already has. For `ollama` the field is `"think": false`. For `openai-compatible` there are three: `"thinking": {"type": "disabled"}`, `"enable_thinking": false` and `"chat_template_kwargs": {"enable_thinking": false}`. A server that rejects them answers with an error that is shown as it is, and the user turns the option off. Never for `anthropic`.

### 6.5 Failures and timeouts

- Before a request, the page checks `permissions.contains` for the base URL's origin. Without the permission the request is not sent (the timeout has not started), and the result is `HostPermissionDenied`.
- Each request gets `AbortSignal.any([cancelSignal, AbortSignal.timeout(ms)])`. An abort caused by the cancel signal is a cancel (no error): the call rejects with the cancel signal's reason (a `DOMException` named `AbortError` unless the caller gave another), which is never an `AppError`, as in the store; callers check `signal.aborted` (`isCancelled(err, signal)`) before treating a rejection as a failure. An abort caused by the timeout is `LLMCallTimeout`. A signal that is already aborted sends nothing.
- A network failure (`TypeError` from `fetch`), an HTTP status other than 2xx, a reply that is not JSON, an error message inside a stream, or a stream that ends before the provider says the reply is complete (`done: true`, a `finish_reason` or `[DONE]`, `message_stop`) is `LLMCallFailed`. Its metadata has the HTTP status and the provider's error message if the body has one (`error.message` or `error`), cut to 300 characters. It never has the request body. A 403 from `ollama` gets the message of section 4.7.
- Servers see the request's `Origin: moz-extension://<uuid>`. Anthropic accepts it because of the `anthropic-dangerous-direct-browser-access` header. Ollama accepts it only if `moz-extension://*` is in its allowed origins (newer versions allow it by default; otherwise `OLLAMA_ORIGINS`). An OpenAI-compatible server that checks origins needs the same.

## 7. Concurrency and lifetimes

- All work runs on the page's single thread with `async` functions. No Web Workers in v1.
- Every cancellable operation takes an `AbortSignal`. A check, an explanation, an alternatives request and a Test connection each own an `AbortController`. Starting a newer one of the same kind, loading a text, or closing the tab aborts it.
- LLM requests run in the tutor page (or the options page for Test connection, or a page-mode frame, section 4.11), so they live as long as that tab. A page-mode frame's requests end when its web page is closed or navigates away. Closing or reloading the tab ends them. A reload loses a running check, and the text is kept (section 4.2).
- The background script registers all its listeners synchronously at the top level, keeps no state in memory between events (what it needs is in `storage.session`), and does no I/O except `storage.session`, `menus`, `notifications`, `runtime` messaging, `tabs` messaging and focusing tabs, and, for page mode (section 4.11), the `page_mode` and `page_mode_sites` settings (it opens the IndexedDB store when an event needs them, and opens it again if the connection was closed), the `<all_urls>` permission, `scripting`, and opening `options.html#welcome` on install.
- **Updates.** An extension update closes the extension's tabs. The background script listens to `runtime.onUpdateAvailable`. It pings the tutor pages (section 4.1) and calls `runtime.reload()` only when none has unsaved changes (with no tutor page open it reloads). Otherwise, or when the pages cannot be asked, the update waits for the next browser start.
- Timeouts: check chunk 15 minutes, explanation and alternatives 120 s, Test connection 60 s. The LLM's *Timeout* replaces the first three. The check timeout applies to each chunk.

## 8. Saving text

The logic is in `src/tutor/saving.ts` (`SavingFlow`, no DOM; the page gives it the editor through a small host interface and the dialogs through two askers, so that tests use fakes) and `src/core/files` (names, decoding, the tab's text state). One operation runs at a time: a click while another one waits for a dialog, a file or a download is ignored. A failure is reported to the banner and never thrown to the caller.

**Files**
- **New** (and Clear) starts an empty text with a new `session:` source (and no name, no document, `lf`), asking first if there are unsaved changes. The old banner is hidden: it belonged to the old text.
- **Open** shows the file chooser (`.txt`, `.md`, `text/plain`, `text/markdown`; a click on the hidden `<input type="file">`). The file is read before anything is replaced (`readTextFile`):
  - A file over 10 MB (10 × 1024 × 1024 bytes; also one that turns out bigger when read) or one that cannot be read is `FileReadFailed`. One that is not valid UTF-8 (`TextDecoder` with `fatal: true`), or has a NUL byte, is `FileNotUTF8`. The route is `SavingFlow.openFile->readTextFile->FileReadFailed`, or `...->readTextFile->decodeTextFile->FileNotUTF8`. The failure goes to the banner and leaves the current text, its name, its source and its unsaved flag alone; nothing is asked.
  - A leading BOM is dropped. If the file has `\r\n` line breaks anywhere, the text remembers `crlf`; every line break (`\r\n` and a lone `\r`) becomes `\n` in the editor, as a textarea does to its value, so the text is exactly what the editor holds.
  - Only after a successful read is the user asked about unsaved changes. Then the text gets the file's name without its last extension (`.hidden` keeps its dot, a name that is only an extension gives no name) and a new `session:` source. It is not a library document and not unsaved.
- **Save** downloads the text under its name: the text goes to a blob URL (`text/plain;charset=utf-8`), written with the remembered line ending (`\n` becomes `\r\n` for `crlf`), and `downloads.download({ url, filename, saveAs: false })`. The file name is the text's name with `.txt` added when it has no extension (a dot and one to four letters or digits at the end: `notes.md` and `report.2024` have one, `Dr.Smith` and `v1.2 draft` do not). Characters a file name cannot have (`/ \ : * ? " < > |` and control characters) become `_`, dots and white space at the start and end go (the browser refuses `..` and paths), the name is at most 120 code points with its extension, and nothing left gives `Untitled`. A text without a name behaves like Save As. Only one download runs at a time.
- **Save As** does the same with `saveAs: true`, so Firefox shows its save dialog. The proposed name is the text's name, or, without one, the text's default title (below), plus `.txt`. Cancelling the dialog is not an error (the wrapper sees `downloads.download` reject with a message that says the download was cancelled, or an interrupted download whose error is `USER_CANCELED`): nothing changes and no banner shows. The name the user typed becomes the text's name (the path from `downloads.search` by download id, its last part without the extension), unless the text is a library document: that keeps its title, which is what the next Save to library writes.
- The wrapper (`src/platform/downloads.ts`, `BrowserDownloads`, over `downloads` and `URL.createObjectURL`; a fake exists) puts its `downloads.onChanged` listener on *before* it starts the download (a small file can finish before `download` has returned its id), waits for `complete` or `interrupted`, revokes the blob URL when the download ends (success, failure, cancel or abort), and removes the listener. Its call takes `{ signal }`; an abort cancels the download and rejects with the signal's reason.
- After a successful download the text is not dirty any more, unless it was edited while the download ran. A failed download is `FileWriteFailed` ("The browser could not save the file."; the browser's own message is only the error's `cause`). The route is `SavingFlow.download->BrowserDownloads.download->FileWriteFailed`; the text stays unsaved. The source does not change.
- **Headless Firefox** has no file picker: `downloads.download({ saveAs: true })` fails there with "An unexpected error occurred", which shows as `FileWriteFailed`. The screenshot harness therefore cannot capture Save As's native dialog and shows this failure instead; Save, with `saveAs: false`, works headless and the harness checks the downloaded file.

**Library**
- **Save to library** stores the text as a document (title, content, line ending, timestamps). For a text that is not a library document, an in-page dialog (`TitleDialog`) asks for the title. The default is the text's name if it has one, otherwise its **default title**: the first line that is not only white space, trimmed and cut to 60 code points (never inside a surrogate pair; "Untitled" when there is none). The title is trimmed, cannot be empty (the dialog says so and stays open), and has at most 200 code points. The document is created, a `session:` source moves to `doc:<id>` (section 5.7), the text is named after the title and is no longer dirty, and the page announces `library-changed` and `stats-changed`. Cancelling the dialog stores nothing.
- A text that came from the library updates its document instead, without asking for a title (a title is changed with Rename): it replaces content and line ending, keeps the document's title, and announces `library-changed`. (`Store.updateDocument` replaces the title too, so the flow passes the tab's name, which follows the library.)
- The **Library** dialog (`LibraryDialog`, a modal `<dialog>`, `#library-dialog`) lists documents by last update, newest first, each with its title, its date (`YYYY-MM-DD`, like the Statistics dialog), its word count, and **Open**, **Rename** and **Delete** buttons; an empty library says so. Delete asks inside the dialog first ("Delete “title” from the library? This cannot be undone."). A failure shows its message in a banner inside the dialog and the list is read again. The dialog follows `library-changed` from other tabs.
  - **Open** reads the document again, then asks about unsaved changes, then loads its content, title, line ending and the `doc:<id>` source, and closes the dialog. Cancelling the question leaves the dialog open. A document that was deleted meanwhile is `DocumentNotFound` in the dialog's banner.
  - **Rename** opens the title dialog with the heading "Rename" and the current title; the store sets the title and `updated_at`; `library-changed` goes out. Renaming the open document updates the tab title.
  - **Delete** deletes the document and announces `library-changed`. Deleting the open document detaches it (the tab keeps its text, name and source key, but no document), so the next Save to library creates a new one and moves the mistakes of that `doc:<old id>` source to the new document.
- Saving to a document deleted meanwhile (`Store.updateDocument` fails) is `DocumentNotFound` ("The library document no longer exists.") in the banner, with the route `SavingFlow.saveToLibrary->Store.updateDocument->DocumentNotFound`, and detaches the text. This also holds when the Save comes from the unsaved-changes dialog: the action is cancelled.
- A tutor tab with a library text follows `library-changed` (and reads the library once when the page loads with a restored library text): a document renamed elsewhere renames the tab, a document deleted elsewhere detaches it. The text itself is never replaced: two tabs can have the same document open, and the last save wins (section 13).

**Unsaved changes.** Before New, Clear, Open (after the file was read) and opening a library document (after it was read), a text with unsaved changes gets an in-page dialog (`UnsavedDialog`, `#unsaved-dialog`, a modal `<dialog>` with `role="alertdialog"`) with **Save**, **Discard** and **Cancel**; `Escape` and a click outside the box are Cancel. It says which text ("“name” has changes that are not saved." or "This text has changes that are not saved.") and what Save does ("Save downloads the text as a file." / "Save updates the document in the library."). Save means Save to library for a library text (an update, with no title dialog), otherwise Save (a download, which for a text without a name is Save As). If it fails or is cancelled, the action is cancelled too; a failure shows its banner.

Issues are not saved. A loaded text has to be checked again, and its recorded mistakes are not counted twice.

**Loading a text.** The page's `loadText` (used by New, Clear, Open and a library document) cancels a running check (the pending check is ended without an outcome, so no "Check cancelled" shows, and its late result is ignored), closes the Alternatives panel, stops a waiting auto-check, puts the text in the editor with the caret at the start and the scroll at the top, calls `TrackedText.load` (which clears the issues, the selection and the explanation, section 5.5), and redraws the mirror, the status bar and the buttons. No `input` event is sent, so the text is not an edit.

## 9. Data storage

All data stays in the user's Firefox profile and is removed when the extension is uninstalled.

**IndexedDB** database `english-tutor`. Version N is reached by running migrations 1..N in order from `onupgradeneeded` (`src/core/store/migrations.ts`). A released migration is never changed. Times are milliseconds since the epoch.

| Object store | Key | Fields | Indexes |
|---|---|---|---|
| `llm_configs` | `id` (auto) | `name`, `provider`, `model`, `base_url`, `api_key`, `temperature`, `timeout_seconds`, `max_parallel`, `no_thinking`, `created_at`, `updated_at` | `name` (unique) |
| `documents` | `id` (auto) | `title`, `content`, `line_ending`, `created_at`, `updated_at` | `updated_at` |
| `error_events` | `id` (auto) | `error_type`, `category`, `snippet`, `source_key`, `fingerprint`, `llm_name`, `created_at` | `[source_key, fingerprint]` (unique), `[error_type, created_at]`, `created_at`, `source_key` |
| `llm_usage` | `id` (auto) | `llm_name`, `kind`, `input_tokens`, `output_tokens`, `estimated`, `created_at` | `created_at` |
| `settings` | `key` | `value` | |

Migration 1 creates all five stores. An index is named after its key path fields joined by `_`, so the compound ones are `source_key_fingerprint` and `error_type_created_at`. `line_ending` is `"lf"` or `"crlf"`. Optional numbers (`temperature`, `timeout_seconds`) are `null` when not set; `base_url` and `api_key` are `""` when not set.

**Settings keys:** `selected_llm_id`, `auto_check`, `auto_check_delay_s`, `editor_font_family`, `editor_font_size`, `button_font_family`, `button_font_size`, `results_font_family`, `results_font_size`, `pane_sizes`, `page_mode`, `page_mode_sites`. `pane_sizes` holds two percentages, stored as the array `[editor, issues]`: the editor's share of the width, and the issues list's share of the right column (each above 0 and below 100). A missing or invalid value gives the default: auto-check off, delay 3 (1 to 60), sizes 13 / 11 / 11 (outside 6 to 48 is invalid), default font families (a family over 100 characters is invalid), no selected LLM (anything but a positive integer is invalid), panes 65 / 40, page mode not offered (`page_mode` false), no site choices (`page_mode_sites` is an object from host name to `"on"` or `"off"`; each host name is lower case, not empty and at most 253 characters, and a site with no entry is `ask`). Reading never fails on a bad stored value; setting a setting to a value that would read back as invalid is refused with `SettingInvalid`.

**`storage.session`** (only the background script, the tutor pages and the options page can use it; an extension frame in a web page cannot, section 4.11): hand-off entries (section 4.1: key `handoff:<uuid>`, value `{ text, action, at }`), the page-mode frame registrations (section 4.11: key `page-frame:<uuid>`, value `{ tabId, at }`) and the Not-an-error ignore set (section 5.7: one `ignore:<source>|<fingerprint>` key per pair, value `true`). Cleared when the browser closes.

**`sessionStorage`** of each tutor tab: its text and text state, one JSON value under `english-tutor-tab` (section 4.2).

**API keys** are stored as plain text in IndexedDB, inside the Firefox profile. The options page says so. Keys are never logged, put in error metadata or messages, or sent anywhere except the LLM's own server.

The `Store` class is constructed with an open `IDBDatabase` and a `Clock`, so tests use `fake-indexeddb` and a fresh database per test. The store does not check the values of an LLM configuration: the `llm` package supplies a validator (`LLMConfigInvalid`) that is passed to the store's constructor. There is no module-level database variable.

### 9.1 Logging

A small logger (`src/core/log.ts`) writes to the console of the page or background script: `debug`, `info`, `warn`, `error`, each with a message and a flat object of fields. Errors are logged with `{ err }`, and the logger expands an `AppError` into tag, route, metadata and the cause's name and message. It logs timings, token counts, sizes and status codes. It never logs the user's text, LLM replies, API keys or hand-off contents. No log is stored.

## 10. Error handling

All errors are `AppError` (CLAUDE.md). Each failure below has its own tag and a route test.

| Tag | Where | When |
|---|---|---|
| `DatabaseOpenFailed` | `store` | the IndexedDB database cannot be opened |
| `MigrationFailed` | `store` | a numbered migration fails, or the upgrade is blocked |
| `DatabaseQueryFailed` | `store` | any other request on configs, documents or settings fails |
| `LLMConfigNameTaken` | `store` | duplicate LLM name |
| `LLMConfigInvalid` | `llm` / `store` | missing name or model; missing or malformed base URL; missing key for `anthropic`; temperature outside 0 to 2; timeout outside 10 to 3600 s (empty or 0 is allowed); parallel requests not a whole number from 1 to 16 |
| `LLMConfigNotFound` | `store` | the selected LLM id does not exist |
| `SettingInvalid` | `store` | a setting is set to a value its key does not allow (for example a size outside 6 to 48) |
| `DocumentNotFound` | `store` | the library document does not exist |
| `ErrorEventSaveFailed` | `store` | recording mistakes or moving a source fails (the underlines are still shown) |
| `StatsQueryFailed` | `store` | reading counts for the header, badges or the Statistics dialog fails |
| `StatsResetFailed` | `store` | Reset statistics, Reset token usage or Not an error fails |
| `UsageSaveFailed` | `store` | storing a request's token usage fails (the result is still shown) |
| `UsageQueryFailed` | `store` | reading the Token usage tab fails |
| `ContextMenuFailed` | `platform` | making, changing or refreshing a context menu entry fails (the page or the background script logs it and goes on without the menu) |
| `ClipboardWriteFailed` | `platform` | Copy in the Alternatives panel cannot write to the clipboard (the panel says so under the list) |
| `LinkOpenFailed` | `platform` | a link of an explanation cannot be opened in a new tab (`tabs.create` fails) |
| `UnknownProvider` | `llm` | the provider string is not supported |
| `HostPermissionDenied` | `llm` / `platform` | the origin of the LLM's base URL is not granted, or the user refused it |
| `LLMCallFailed` | `llm` | network failure, non-2xx status, or a broken stream |
| `LLMCallTimeout` | `llm` | the request exceeded its timeout |
| `LLMResponseInvalid` | `analysis` | the reply does not fit the contract (or has no usable alternative), even after one retry; or an empty explanation |
| `SelectionEmpty` | `analysis` | alternatives or a selection check for an empty or white-space selection |
| `SelectionTooLong` | `analysis` | alternatives for a selection over 600 words |
| `FileReadFailed` | `core` | the file cannot be read, or is over 10 MB |
| `FileNotUTF8` | `core` | the file is not valid UTF-8, or contains a NUL byte |

## 13. Risks and open points

- **LLM quality varies.** Small local models may return invalid JSON or invent errors. Mitigated by the retry, the strict locator and the user's choice of model, as in the desktop app.
- **Origins.** Ollama and some OpenAI-compatible servers check the `Origin` header and may refuse `moz-extension://`. The message names the fix for Ollama. Other servers depend on their own settings.
- **Distribution.** Firefox release builds install only signed extensions. Signing through addons.mozilla.org (listed or unlisted) is not part of v1. Until then the extension is loaded as a temporary add-on (`about:debugging`, or `web-ext run`), or unsigned in Developer Edition / Nightly.
- **Plain-text API keys** in the Firefox profile, as in the desktop app. Encrypting them with a user passphrase is a possible later change.
- **Long selections from web pages** may be shortened by Firefox in `info.selectionText`. Reading the selection with `scripting` and `activeTab` would avoid this, at the cost of two permissions.
- **Statistics do not follow files.** Without file paths, opening the same file again starts a new source and can count its mistakes again. Saving to the library is the way to keep one identity.
- **Two tabs, one document.** The last save to the library wins. There is no lock or merge in v1.
- **No data export.** Uninstalling the extension deletes the library and the statistics. Export and import (JSON) are candidates for later.
- **Page mode sends what the user types on websites to the LLM.** It is off by default, it can be turned off per site, it skips password, payment and code fields, and it reads only text boxes the user focuses. A cloud LLM still receives that text; the options page says so.
- **Page mode's prompt and its access.** Once the user allows it, the content script runs on every site, but on a site that is not `on` it only waits for a focus: it reads no text and makes no frame. The prompt is drawn by the content script in a closed shadow root, so the page cannot read it or click it (untrusted events are ignored), and clicks in its first 500 ms are ignored. A page could still draw something over it to trick the user into a click; the prompt only turns page mode on for that page's own host, which is what such a page could ask for openly anyway. Sites are host names, not registrable domains: a user on a site with many subdomains is asked once per subdomain.
- **Page mode's frame address.** A web page can embed `page-ui.html` itself if it knows the extension's `moz-extension://` address (it differs for every install, but Firefox has had ways for pages to learn the address of a web accessible resource), and could then offer the frame a port with an id of its own choosing. The frame therefore starts only for an id that the content script of the same tab registered with the background script, once (section 4.11), so such a frame does nothing and the page cannot use the user's LLM. What is left: a script of the page that runs in the same tab would need the id of the real frame, which lives only in the closed shadow root and in the frame's address inside it, and it is used once, when the frame loads; the page cannot read either. The id stops being valid as soon as the real frame has claimed it, so a page that learns it later gains nothing.
- **Page mode and complex editors.** Mirrors follow the computed styles of plain text boxes well. Sites that restyle or re-render their editors on every key (rich `contenteditable` editors) can make underlines lag or drift for a frame. Canvas-based editors are not supported. Sites that keep the frame from answering (for example with `Content-Security-Policy: sandbox`) get `PageFrameBlocked`.
- **Not decided yet:** applying a correction inside a web page's text box, the explanation language, and whether the category colours become configurable.
